# Execution plan – Projects (S1-01)

Source doc: .ai/specs/2026-10-26-projects.md
Plan task: S1-01 (docs/plan/implementation-plan.md)
Spec PR: #111 (merged)
Branch: S1-01-projects

## Goal

Implement the approved change specification for projects: the `projects` and `project_members` model, the project endpoints with their CASL rules, the archived restriction and `allowedActions`, membership management with the project-scoped member candidates, the web feature `features/projects/` (Projects page, New project dialog, project settings), the getting-started item, the demo dataset and the user documentation – the reference implementation of the feature-module pattern (§18.9).

## Scope

- Server: `apps/server/prisma/` (models, enums, migration with the key check constraint and the audit `details` column of Q14), `apps/server/src/modules/projects/`, `apps/server/src/platform/authorization/` (Prisma-backed record access for `Project`, the `@casl/prisma` client extension on `PrismaService`), `apps/server/src/modules/audit-log-entries/` (new actions, typed `details`), `apps/server/src/modules/users/` (`create_project` on `/users/me`), `apps/server/src/modules/administration/` (getting-started item), the demo dataset and factories.
- Contracts: `packages/contracts/src/projects/`, error codes.
- Web: `apps/web/src/features/projects/`, routes `app/(team)/projects/…`, navigation, catalogues EN/PL (`packages/i18n`).
- Docs: `docs/user/` (EN, PL), the system specification sections listed in the spec, §18.9 reference paths, the spec moved to `implemented/`, plan task S1-01 ticked.

## Non-goals

As in the spec: no GitHub, SLA or WIP settings; no key immutability after the first ticket (S1-05); no invitations by e-mail (S1-03); no organizations (S1-02); no full §7.5 matrix or token scopes (S1-04); no product tour.

## Implementation Plan

### Phase 1: Model and API

1. Prisma models, enums, migration with the key check constraint and the audit `details` column; contracts `@trybun/contracts/projects`; enum equality test; factories.
2. `@casl/prisma` and its `PrismaService` client extension; `projects.abilities.ts` with the archived restriction; `RecordAccess` for `Project`; `create_project` on `/users/me`; `projects.abilities.spec.ts`.
3. Create, read, list, update with `If-Match`, field-level `403` and `project.key_taken`; integration tests.
4. Archive, unarchive, delete with audit entries; the archived-project integration test over every write endpoint.
5. Members: list, add, change role, remove, with audit entries (`details`), the project-row lock against a concurrent archive; member candidates; integration tests.
6. `pnpm api:generate`.

### Phase 2: Web, documentation, checklist

7. `features/projects/` queries, mutations, components; Projects page and the navigation item; New project dialog with key suggestion; component tests.
8. Settings page: General, Members and Danger zone tabs, Undo for archiving, last-Project-manager warning, archived banner.
9. Getting-started item "Create a project"; demo dataset.
10. User documentation EN and PL; `pnpm help:generate`.
11. E2E (phone, tablet, desktop, axe).
12. System specification updates, §18.9 reference paths, spec moved to `implemented/`, plan task ticked.

## Risks

- `@casl/prisma` is a new runtime dependency (Rule 10: stable version, cooldown, no vulnerabilities).
- The archived restriction and the Prisma-backed record access are the first real `RecordAccess`; the request-pipeline tests must keep passing.
- The audit `details` column changes the immutable audit log shared with S1-02 (#112); its trigger must still refuse updates.
- Size: twelve steps across server, contracts and web; the run commits and pushes per phase so `om-auto-continue-pr` can resume.
