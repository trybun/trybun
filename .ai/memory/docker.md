# Docker Compose, images and infrastructure services

Non-obvious behaviour found when the Compose set-up was built (S0-03, October 2026). Rules: [§15.9](../../docs/spec/15-deployment.md), [§15.12](../../docs/spec/15-deployment.md).

- **`docker compose up --wait`** counts a one-off service that is still running as ready and returns before it finishes. In production the API depends on `migrate` and `keycloak-config` with `service_completed_successfully`, so a failed one-off fails the command; `pnpm dev` runs `docker compose … wait keycloak-config` after `up --wait` for the same reason.
- **One image, several services**: only one service (`api`) may have the `build:` section of `ghcr.io/trybun/server`; with the same image name in several `build:` sections `docker compose build` fails with `image … already exists`.
- **Keycloak 26.8** reports `/health/ready` (management port 9000, under `KC_HTTP_RELATIVE_PATH`) as `UP` a few seconds before its first start has created the master realm; requests answer 503 until then. keycloak-config-cli therefore runs with `KEYCLOAK_AVAILABILITYCHECK_ENABLED`. The image has no HTTP client – the health check uses bash `/dev/tcp`. With `KC_HOSTNAME=https://<domain>/auth` and `KC_HOSTNAME_BACKCHANNEL_DYNAMIC=true`, internal calls to `http://keycloak:8080/auth` work while the issuer stays public.
- **keycloak-config-cli** runs `docker/keycloak/apply-config.sh` as its entry point (the image has `sh`, user `nobody`); details in `keycloak.md`.
- **keycloak-config-cli** has no release for Keycloak newer than 26.1 (6.5.1, May 2026); `6.5.1-26.1.0` works against Keycloak 26.8.
- **sjp.pl** keeps only the newest dictionary archive online (older URLs return 404), so `docker/postgres/` keeps the archive with its checksum. The files are ISO-8859-2 and are converted to UTF-8 (including the `SET` line of the affix file) for PostgreSQL. Loading the dictionary takes ~0.3 s per new database connection.
- **SeaweedFS 4.x** creates its S3 admin identity from `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`; anonymous requests get 403. Telemetry is switched off with `-master.telemetry=false` (`-telemetry` is not a flag of `weed server`). Health: `GET :8333/healthz`.
- **Networks**: services only on the `internal: true` network have no DNS and no route outside, and cannot publish ports – `compose.dev.yaml` adds the `outbound` network to the services it publishes. On Linux the host itself can still connect to container IPs of every bridge network (also `internal`); only published ports are reachable from other machines.
- **Integration tests** build `docker/postgres` with Testcontainers (`GenericContainer.fromDockerfile`), because the `polish` migration needs the dictionary; its init script requires `KEYCLOAK_DB_PASSWORD`, otherwise the container stays unhealthy.
- **PostgreSQL 18 images** keep their data in `/var/lib/postgresql/18/docker`; mount the volume at `/var/lib/postgresql`. Scripts in `/docker-entrypoint-initdb.d/` run only when the volume is empty.
- The VPS of the maintainer had neither the Compose nor the buildx plugin; both were installed per user in `~/.docker/cli-plugins/` from the GitHub releases (checksums verified).
- **Dependabot and image pinning** (S0-16): Dependabot's `docker` ecosystem reads only literal `FROM image:tag@sha256:…` lines, never `ARG` defaults – write the pinned image in each `FROM` line. It does not update image strings in TypeScript either: the Testcontainers images in `apps/server/test/` must equal the references of `compose*.yaml` (`scripts/check-supply-chain.js` in `pnpm lint`), so a Dependabot pull request that bumps a Compose image fails lint until the test constant is updated in the same pull request.
