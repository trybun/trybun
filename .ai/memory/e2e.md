# E2E tests and the Lighthouse budget – Playwright, axe, Lighthouse

Non-obvious behaviour found when the E2E set-up was built (S0-08, October 2026, Playwright 1.64, `@axe-core/playwright` 4.14, Lighthouse 13.5). Decisions: [§2.9](../../docs/spec/02-agent-rules.md), [§2.14](../../docs/spec/02-agent-rules.md).

- **Sign-in**: `apps/web/e2e/auth.setup.ts` signs in once as the seeded Developer (password + TOTP of `docker/keycloak/dev/`) and stores the browser state for all projects. Keycloak accepts a one-time code only once, so a second sign-in in the same 30-second window fails with "Invalid authenticator code."; `SignInPage` waits for the next code. Tests must not sign out with the shared state – that ends the Keycloak session of every other test.
- The Keycloak login page has its own `banner` landmark; wait for an element of the application (the account menu) to know the sign-in completed.
- The React Compiler check (`e2e/react-compiler.spec.ts`) found no React roots through the stubbed DevTools hook on WebKit in CI (#66); it runs in the Chromium projects only.
- **WebKit** (the iPad project) needs system libraries: `playwright install --with-deps chromium webkit` (CI). On a machine without them, check the tablet project by temporarily setting `browserName: 'chromium'`.
- **axe**: exclude `[data-base-ui-focus-guard]` as in Storybook (`e2e/accessibility.ts`). Run it on an open popup only after its opening animation (`fade-in-0`, 100 ms) has finished – `AppShellPage.openedMenu()` awaits `getAnimations({ subtree: true })`; mid-fade the text is semi-transparent and `color-contrast` fails now and then (#72).
- **Lighthouse** has no Playwright integration: `e2e/lighthouse.spec.ts` starts a persistent Chromium context with `--remote-debugging-port` (Lighthouse opens its tab in the default context, which only a persistent context shares with the cookies) and calls `lighthouse(url, { port })`. Playwright's `expect` has no asymmetric numeric matchers (`expect.toBeGreaterThanOrEqual`); use `expect.soft` per metric.
- The default Lighthouse configuration is the mobile profile with simulated throttling (Lantern): the simulated LCP counts every request started before the observed LCP – also the `async` scripts in `<head>`. Client JavaScript therefore moves the LCP even when the observed LCP equals the FCP. Zod in the client bundle (≈ 60 KB gzip) pushed the shell from 2.3 s to 2.9 s; `dataOf()` imports the Problem Details parsing dynamically for that reason.
- The sign-in redirect page navigates to Keycloak at once, and Lighthouse reports the final page. Blocking `*/api/auth/signin/*` (`blockedUrlPatterns`) keeps the measurement on the page of the web application; blocking `*/api/auth/*` sends Auth.js to its error page instead. The Keycloak login screen (`keycloak.v2`) scored Performance 0.74, LCP 4.7 s (October 2026).
- `next start` warns that it "does not work" with `output: 'standalone'`, but serves the same build; the E2E web server uses it, the image runs `apps/web/server.js`.
- **Several seeded sign-ins** (S0-10): the seeded accounts share one TOTP secret, and Keycloak rejected the second account's code in the same 30-second window as "Invalid authenticator code.". The sign-ins of `auth.setup.ts` run serially with a 90-second timeout, so the wait for the next code fits. Each account has its own storage state (`storage-state.ts`).
- **Tour tests**: the developer has completed every tour (demo dataset), so tours never interrupt other tests; the newcomer's setup runs `pnpm --filter @trybun/server db:seed` first, which restores her empty tour progress. A test of one person on two devices opens its own contexts with `browser.newContext({ ...devices[…], storageState })` and runs in one project only.
- **Product tours and the LCP budget** (S0-10): adding `TourTip` (Base UI Popover and Drawer) to the shell bundle pushed the simulated LCP of the empty shell in CI to 2.59 s (budget 2.5 s; locally it still passed). The tip is loaded with `lazy()` only when a tour runs (`product-tour-step-tip.tsx`). Code that only some sessions need goes into a lazily loaded component.
- **The simulated LCP of the empty shell** (#72, October 2026): the observed LCP (the server-rendered `h1`) is at ~80 ms, and Lantern counts every request that starts before it – the whole document, CSS, preloaded fonts and all ~255 KB (gzip) of client JavaScript, ≈ 300 KB in total – plus the CPU tasks before it at 4× slowdown. The same build therefore varies in steps of ~200 ms between runs locally (whether a large script is evaluated before the first paint), while CI gave the same value on re-runs; re-running a failed budget check does not help. Blocking requests with `blockedUrlPatterns` does not show their weight – a blocked request stays in the graph. What moved it: preloading only the `latin` subset of Manrope (`subsets` of `next/font` are the preloaded files; `latin-ext` keeps its `@font-face` with `unicode-range` and loads for Polish letters only) and importing `next-auth/react` on sign-out – median 2.55 → 2.35 s locally. In CI it still gave 2.64 s (#71): CI lands on the upper step. What brought it to ~1.90 s locally (stable over 6 runs): loading the header menus – and Base UI's `Menu` (~57 KB gzip) with them – with `lazy()` behind a `Suspense` boundary (`lazy-user-menu.tsx`, `lazy-help-menu.tsx`, `lazy-product-tour-menu-items.tsx`). Every client module a server component imports joins the initial chunks, so the tour items passed as children of the help menu had to be lazy too; with only the menus lazy, Base UI stayed. The server still renders the menus, but on the first request of a route after a start of `next start` a lazy component suspends once and is streamed after the page: E2E tests wait with `toBeVisible()` before `boundingBox()`, and unit tests render with `prerender` of `react-dom/static` instead of `renderToStaticMarkup`, which does not wait for `Suspense`.
- **TBT and a busy runner** (#146, October 2026): the simulated TBT multiplies the main-thread tasks Lighthouse observes by the 4× CPU slowdown, so whatever else runs on the machine moves it. With `fullyParallel` the Lighthouse tests ran beside the device projects (CI: 2 workers) and failed now and then on TBT 223 ms for unchanged code. Locally the empty shell gave TBT 58–67 ms on an idle machine and 308–444 ms beside 8 busy CPU loops; the sign-in redirect 80–141 ms idle. The `lighthouse` project therefore depends on the device projects and runs with `workers: 1`. A failing device test skips the budget (`did not run`); `--project=lighthouse --no-deps` measures alone against a running environment. Judging the median of several runs instead of every run was rejected: it would loosen the acceptance rule of §2.9, a change of requirements.
- **Navigation and the LCP budget** (S0-12): reading the current account with `useQuery(currentUserQueryOptions(browserApiClient))` in the side and bottom navigation pulled the browser API client (`openapi-fetch`) into the first load of the shell and moved the simulated LCP to 2.55 s. The team layout passes `allowedActions` of its prefetched account to `AppShell` as a prop instead; only the lazily loaded menus use the query.
- **Measuring an element** (2026-10-25): `await expect(target).toBeVisible()` followed by `target.boundingBox()` is a race – the lazily loaded menus of the header (#72) and the help results, rendered again after hydration, replace the element in between, and `boundingBox()` returns `null` (the help touch-target test failed on the tablet in CI, also on `main`). Measure with `expect.poll()`, as `expectTouchTarget()` of `e2e/touch-targets.ts` does.
- **Test environment for QA skills** (S1-01; its own Compose project `trybun-test` since S1-02 – it refuses while another project publishes 5432, 6379, 8333, 8080, 3310, 8025 or 1025, e.g. `pnpm dev`; keep `-p trybun-test` when regenerating the scripts with `om-prepare-test-env`): `sh .ai/scripts/test-env-up.sh` brings up the local environment the way CI's E2E job does (Compose, migrations and the demo dataset, production builds of the API on 3001 and the web application on 3000), reuses a healthy running one in seconds, skips the build when the sources did not change, and writes `.ai/qa/test-env.json` for `om-auto-qa-pr` and `om-integration-tests`; `sh .ai/scripts/test-env-down.sh` stops only what it started (it leaves a Compose stack of `pnpm dev` that was already running). It refuses to start while `pnpm dev` serves 3000/3001. Without a `.env` it creates one from `.env.example`, which then fails two tests of `backchannel-logout/route.integration.spec.ts` in `pnpm test:coverage` (400 instead of 200; they pass alone and without the file) – delete a `.env` the script created before running the coverage suite (#139).
- **One-time codes in QA runs** (#141): `TEST_TOTP_SECRET` of `.ai/qa/test-env.env` is the Base32 form of the OTP secret (for authenticator apps and `oathtool --base32`); an HMAC over its raw bytes gives a wrong code ("Invalid authenticator code."). Decode it first, or compute the code from the raw secret as `apps/web/e2e/totp.ts` does. Keycloak refuses a code twice in one 30-second window, so a scripted run with several sign-ins waits for the next window before entering the code. In agent-browser, `set headers` with `Accept-Language` did not switch the language of the web application or the Keycloak screen; the Polish screen is covered by `e2e/sign-in.spec.ts`.
- **agent-browser on the VPS** (S1-01): Chrome for Testing aborts with "No usable sandbox" (Ubuntu blocks unprivileged user namespaces through AppArmor) and with "Socket path too long" under the long `TMPDIR` of Cezar sessions. `.ai/scripts/test-env-browser.sh` runs it with `TMPDIR=/tmp` and `--no-sandbox` (Playwright launches Chromium without the sandbox too); `agent-browser doctor` still reports its own launch test as failed, because it ignores these arguments.
- **Invitations** (S1-03): an invited address of `customer.example.com` joins the demo organization on acceptance and breaks the member count of `organizations.spec.ts` running in parallel – the E2E invites `@example.org` (personal access). The API builds the link from `TRYBUN_DOMAIN` (`https://localhost/invitations#token=…` locally): open its path and fragment on the base URL (`InvitationPage.goto`). A new person needs a context of their own (`browser.newContext({ ...testInfo.project.use, storageState: { cookies: [], origins: [] } })`). `getByLabel` of a text that is both a radio choice card and a field label matches the radio, its hidden input and the field – use `getByRole('textbox' | 'combobox', { name })`; a dialog's accessible name follows its current title ("Add member" → "Invitation created"). `navigator.clipboard.readText()` needs `grantPermissions(['clipboard-read', 'clipboard-write'])` and is checked in Chromium only.
- **Accounts page invitations** (S1-03): GitHub sign-in is not configured in the E2E environment, so an invitation to the Administrator role (or any team target) is refused with `invitation.github_sign_in_missing` – the E2E checks that refusal and runs the flow with an end-user target. The server-rendered **Invite** button of the page opens nothing when clicked before the hydration: `AccountsPage.openInvite()` retries with `toPass()`. A pending invitation of an interrupted run stays in the project, so assertions on pending rows filter by the run's own address. The multi-device deactivation test of `accounts.spec.ts` ends Marek Manager's sessions and signs him in again, which breaks `invitations.spec.ts` (manager storage state) when both run in the full suite.
