# E2E tests and the Lighthouse budget – Playwright, axe, Lighthouse

Non-obvious behaviour found when the E2E set-up was built (S0-08, October 2026, Playwright 1.64, `@axe-core/playwright` 4.14, Lighthouse 13.5). Decisions: [§2.9](../../docs/spec/02-agent-rules.md), [§2.14](../../docs/spec/02-agent-rules.md).

- **Sign-in**: `apps/web/e2e/auth.setup.ts` signs in once as the seeded Developer (password + TOTP of `docker/keycloak/dev/`) and stores the browser state for all projects. Keycloak accepts a one-time code only once, so a second sign-in in the same 30-second window fails with "Invalid authenticator code."; `SignInPage` waits for the next code. Tests must not sign out with the shared state – that ends the Keycloak session of every other test.
- The Keycloak login page has its own `banner` landmark; wait for an element of the application (the account menu) to know the sign-in completed.
- The React Compiler check (`e2e/react-compiler.spec.ts`) found no React roots through the stubbed DevTools hook on WebKit in CI (#66); it runs in the Chromium projects only.
- **WebKit** (the iPad project) needs system libraries: `playwright install --with-deps chromium webkit` (CI). On a machine without them, check the tablet project by temporarily setting `browserName: 'chromium'`.
- **axe**: exclude `[data-base-ui-focus-guard]` as in Storybook (`e2e/accessibility.ts`). Run it on an open popup only after its opening animation (`fade-in-0`, 100 ms) has finished – `AppShellPage.openedMenu()` awaits `getAnimations({ subtree: true })`; mid-fade the text is semi-transparent and `color-contrast` fails now and then (#72).
- **Lighthouse stays on 13.5** (#274, November 2026): 13.6 pulls in `sentry` (FSL-1.1-Apache-2.0, source-available) through `@sentry/node` 11, which fails the license check of Dependency review (§2.14). The maintainer kept the policy without an exception: `apps/web/package.json` has `~13.5.0` and `.github/dependabot.yml` ignores `>=13.6.0`. Lift both when an upstream release drops the dependency.
- **Lighthouse** has no Playwright integration: `e2e/lighthouse.spec.ts` starts a persistent Chromium context with `--remote-debugging-port` (Lighthouse opens its tab in the default context, which only a persistent context shares with the cookies) and calls `lighthouse(url, { port })`. Playwright's `expect` has no asymmetric numeric matchers (`expect.toBeGreaterThanOrEqual`); use `expect.soft` per metric.
- The default Lighthouse configuration is the mobile profile with simulated throttling (Lantern): the simulated LCP counts every request started before the observed LCP – also the `async` scripts in `<head>`. Client JavaScript therefore moves the LCP even when the observed LCP equals the FCP. Zod in the client bundle (≈ 60 KB gzip) pushed the shell from 2.3 s to 2.9 s; `dataOf()` imports the Problem Details parsing dynamically for that reason.
- The sign-in redirect page navigates to Keycloak at once, and Lighthouse reports the final page. Blocking `*/api/auth/signin/*` (`blockedUrlPatterns`) keeps the measurement on the page of the web application; blocking `*/api/auth/*` sends Auth.js to its error page instead. The Keycloak login screen (`keycloak.v2`) scored Performance 0.74, LCP 4.7 s (October 2026).
- `next start` warns that it "does not work" with `output: 'standalone'`, but serves the same build; the E2E web server uses it, the image runs `apps/web/server.js`.
- **Several seeded sign-ins** (S0-10): the seeded accounts share one TOTP secret, and Keycloak rejected the second account's code in the same 30-second window as "Invalid authenticator code.". The sign-ins of `auth.setup.ts` run serially with a 90-second timeout, so the wait for the next code fits. Each account has its own storage state (`storage-state.ts`).
- **Tour tests**: the developer has completed every tour (demo dataset), so tours never interrupt other tests; the newcomer's setup runs `pnpm --filter @trybun/server db:seed` first, which restores her empty tour progress. A test of one person on two devices opens its own contexts with `browser.newContext({ ...devices[…], storageState })` and runs in one project only.
- **Product tours and the LCP budget** (S0-10): adding `TourTip` (Base UI Popover and Drawer) to the shell bundle pushed the simulated LCP of the empty shell in CI to 2.59 s (budget 2.5 s; locally it still passed). The tip is loaded with `lazy()` only when a tour runs (`product-tour-step-tip.tsx`). Code that only some sessions need goes into a lazily loaded component.
- **The simulated LCP of the empty shell** (#72, October 2026): the observed LCP (the server-rendered `h1`) is at ~80 ms, and Lantern counts every request that starts before it – the whole document, CSS, preloaded fonts and all ~255 KB (gzip) of client JavaScript, ≈ 300 KB in total – plus the CPU tasks before it at 4× slowdown. The same build therefore varies in steps of ~200 ms between runs locally (whether a large script is evaluated before the first paint), in CI too (#163: `b8cf3be` gave 2659 ms and passed on a re-run). Blocking requests with `blockedUrlPatterns` does not show their weight – a blocked request stays in the graph. What moved it: preloading only the `latin` subset of Manrope (`subsets` of `next/font` are the preloaded files; `latin-ext` keeps its `@font-face` with `unicode-range` and loads for Polish letters only) and importing `next-auth/react` on sign-out – median 2.55 → 2.35 s locally. In CI it still gave 2.64 s (#71): CI lands on the upper step. What brought it to ~1.90 s locally (stable over 6 runs): loading the header menus – and Base UI's `Menu` (~57 KB gzip) with them – with `lazy()` behind a `Suspense` boundary (`lazy-user-menu.tsx`, `lazy-help-menu.tsx`, `lazy-product-tour-menu-items.tsx`). Every client module a server component imports joins the initial chunks, so the tour items passed as children of the help menu had to be lazy too; with only the menus lazy, Base UI stayed. The server still renders the menus, but on the first request of a route after a start of `next start` a lazy component suspends once and is streamed after the page: E2E tests wait with `toBeVisible()` before `boundingBox()`, and unit tests render with `prerender` of `react-dom/static` instead of `renderToStaticMarkup`, which does not wait for `Suspense`.
- **TBT and a busy runner** (#146, October 2026): the simulated TBT multiplies the main-thread tasks Lighthouse observes by the 4× CPU slowdown, so whatever else runs on the machine moves it. With `fullyParallel` the Lighthouse tests ran beside the device projects (CI: 2 workers) and failed now and then on TBT 223 ms for unchanged code. Locally the empty shell gave TBT 58–67 ms on an idle machine and 308–444 ms beside 8 busy CPU loops; the sign-in redirect 80–141 ms idle. The `lighthouse` project therefore depends on the device projects and runs with `workers: 1`. A failing device test skips the budget (`did not run`); `--project=lighthouse --no-deps` measures alone against a running environment. Since #163 every value of the budget applies to its median over three runs (§2.9, approved by the maintainer); `computeMedianRun` of Lighthouse is not used, because it picks the run by FCP and TTI, and the FCP of the shell is the same in every run.
- **The LCP steps in CI** (#163, October 2026): over 31 CI runs the simulated LCP of the empty shell landed on ~2000 ms (23), ~2450 ms (5) and 2540–2660 ms (3), at a constant FCP of 915 ms. Lantern keeps in the LCP graph every script that finished downloading before the observed LCP, unless its `EvaluateScript` started after it (`getRenderBlockingNodeData` of `@paulirish/trace_engine`); the paint of the `h1` waits for the stylesheet, which arrives with the async chunks, so on a slower runner the framework chunks – React DOM with the Next.js runtime (~72 KB gzip) and the router (~36 KB) – fall in and add ~450 or ~650 ms. The largest chunk in the graph sets the LCP, so trimming small application chunks barely moves it: an experiment moving the product tours (API client, queries, tour definitions) behind `lazy()` and Zod out of `instrumentation-client.ts` saved 12.9 KB gzip and left the local LCP at ~2020 ms (not merged). `experimental.inlineCss` made it worse (document 8 → 55 KB, LCP ~2230 ms). To see the graph, recompute `LanternLargestContentfulPaint` of `lighthouse/core/computed/metrics/` on the saved artifacts of a run (`result.artifacts`) and print the nodes of `pessimisticEstimate.nodeTimings`; `taskset -c 0` with a busy loop on the same CPU provokes the upper steps locally now and then.
- **Navigation and the LCP budget** (S0-12): reading the current account with `useQuery(currentUserQueryOptions(browserApiClient))` in the side and bottom navigation pulled the browser API client (`openapi-fetch`) into the first load of the shell and moved the simulated LCP to 2.55 s. The team layout passes `allowedActions` of its prefetched account to `AppShell` as a prop instead; only the lazily loaded menus use the query.
- **Zod through a queries module** (#372, November 2026): #359 gave `features/invitations/queries.ts` value imports of `MAX_PAGE_LIMIT` (`@trybun/contracts/pagination`) and `ApiError` (`lib/errors/api-error.ts`, which parses Problem Details), both Zod modules. `ProductTourProvider` read the account kind with `currentUserQueryOptions` of `features/users/queries.ts`, which imports the invitations queries for the Accounts page, so the full Zod API (~28 KB gzip, until then only behind the `await import()` of `dataOf()`) joined the initial chunks of `(team)/layout`: 241.8 → 269.9 KB of client JavaScript in the CI reports, the simulated LCP of the empty shell 2510–2576 ms (median of 3) on `main`. The layout now passes the kind as the `audience` prop; the entry chunks are back at 99.5 KB gzip. To find such a regression: the Playwright report of a failed CI run carries the three Lighthouse reports of each key page as attachments (inline in `index.html`, a base64 zip); compare the script requests of two runs; and list the `entryJSFiles` of `.next/server/app/(team)/page_client-reference-manifest.js` after `next build`, grepping them for `ZodObject`. Since #374 `pnpm build` does this itself (`apps/web/scripts/check-first-load.ts`): it fails when the first load of a shell layout – its `entryJSFiles` and `rootMainFiles` of `build-manifest.json` – contains the quoted `"ZodType"`/`"ZodMiniType"` that every schema class of Zod 4 defines, and prints the gzip size of each first load (234.8 KB on `main` against 262.7 KB just before #373; Lighthouse counted 241.8 and 269.9 KB of transfer). The core's `"$ZodType"` of `instrumentation-client.ts` is in `rootMainFiles` and does not match. `polyfillFiles` are left out: Next.js loads them with `noModule`. Not `ZodObject`: only `z.object` defines it, while every schema class extends `ZodType`.
- **Measuring an element** (2026-10-25): `await expect(target).toBeVisible()` followed by `target.boundingBox()` is a race – the lazily loaded menus of the header (#72) and the help results, rendered again after hydration, replace the element in between, and `boundingBox()` returns `null` (the help touch-target test failed on the tablet in CI, also on `main`). Measure with `expect.poll()`, as `expectTouchTarget()` of `e2e/touch-targets.ts` does. A web-first assertion just before does not help either: the type line of a ticket card passed `toHaveText` and its next `boundingBox()` still returned `null` on the tablet in CI (#322, 2026-11-12; not reproduced locally in 180 tablet runs). The height checks of `ticket-list.spec.ts` poll `heightOf()`, which reads a missing box as infinite so an upper bound keeps polling; two measurements that depend on each other go in one `toPass()` block, so a stale pair is measured again together – as the sharing-action check measures the title cell, the Status cell and both actions (#329).
- **Filtering a run** (#329, 2026-11-13): pass Playwright's options straight after the script – `pnpm e2e --project=tablet --grep "…" --repeat-each 20` (README). `pnpm e2e -- --project=…` forwards a literal `--`, after which Playwright ignores every filter and runs the whole suite (448 tests instead of 40 here); the same holds for `pnpm --filter @trybun/web exec playwright test …`, which takes the options without `--`.

- **Processes a test of `.ai/scripts/` signals** (#452, PR #454, 2026-11-23): a process the test itself spawns (`spawn` from Vitest) and a script then kills stays a zombie while the test waits in `spawnSync`, because Node reaps its children only from the event loop. `process.kill(pid, 0)` and the script's `kill -0 -<pgid>` still see it, so `test-env-down.sh` waits its full 30 s and the test times out instead of failing on its assertion. Start such a process from a shell that exits at once – `execFileSync('sh', ['-c', 'setsid sleep 300 >/dev/null 2>&1 & echo $!'])` – so it is reparented and reaped as soon as it dies; it then leads its own process group under the printed PID, and the cleanup after the test ends it. That cleanup signals a recorded PID only after checking it is still the test's own (#458): once its process has exited the kernel may give the PID to another program. So `stopProcesses()` signals the group of a `start()` script only while Node has not seen it exit, leaves the recorded applications to the run-id check of `test-env-down.sh`, and otherwise reads no recorded PID (`pids`, `grandchildren`): every process of a test carries its tag `SPEC_PROCESS_TAG` (a UUID, in `environment()`), and it kills only the processes whose `/proc/<pid>/environ` holds it – give a process the test starts outside `environment()` the tag too (`reuseRecordedPids()`), or the cleanup leaves it running. The cleanup is an asynchronous `afterEach`, and Vitest's default `hookTimeout` is 10 s (`1e4` outside browser mode, Vitest 5.1). When the hook takes longer, Vitest starts the next test while the hook keeps running, and the new test's `beforeEach` replaces the module-level `tag` and `folder` the cleanup still reads. So such a hook gets its own timeout as its last argument (60 s, as `PROCESS_TESTS`), copies the test's state into locals before its first `await`, and removes the folder in a `finally` (PR #465).
- **`/proc` reads in the shell scripts of `.ai/scripts/` under `set -eu`** (#453, PR #455, 2026-11-23): a process `ps` has just listed can exit before the script reads its `/proc/<pid>/stat` or `environ`. A helper whose last command is that read then exits non-zero, and `x=$(helper)` as a plain command stops the script under `set -e` in dash. A helper called only in an `if` condition is not affected. In `test-env-down.sh` this left the descriptor `stopping` and failed two `--foreground` tests only under the load of `pnpm test:coverage`; the plain `pnpm test` and 20 repeated runs passed. Such helpers end in `|| true` and report a vanished process as empty output (`ticks()` in `test-env-down.sh`); the spec's *finishes the stop when processes of a group exit while it lists them* reproduces the race with 20 short-lived processes.
- **Writes and reads of `.ai/qa/test-env.json`** (#457, 2026-11-23): another process may read the descriptor at any moment (the `--foreground` owner, a reuse check, a QA skill), so the scripts never rewrite it in place. `cat > file` truncates it before writing, and GNU `sed -i.bak` renames it to the backup before it renames the new file into place (seen with `strace`, sed 4.9), so a reader in between sees it empty or missing. Both scripts write `$DESCRIPTOR.$$.tmp` in `.ai/qa` and `mv -f` it over the descriptor, a rename within one directory, which is atomic. A decision that needs several values of it reads it once (`fg_read_descriptor` in `test-env-up.sh`) and takes them from that copy: under the load of `pnpm test:coverage` a `--reset` landed between the owner's separate reads of `status` and `runId`, and it logged `stopped elsewhere (running)` instead of `was replaced by <run>`. The spec's *when a replacement lands while it reads the descriptor* puts the replacement after a chosen read with stubs of `cat` and `sed` that count the reads of the descriptor; *the descriptor (#457)* holds it open across a boot and a down and checks that the old copy stays whole.
- **One-time codes in QA runs** (#141): `TEST_TOTP_SECRET` of `.ai/qa/test-env.env` is the Base32 form of the OTP secret (for authenticator apps and `oathtool --base32`); an HMAC over its raw bytes gives a wrong code ("Invalid authenticator code."). Decode it first, or compute the code from the raw secret as `apps/web/e2e/totp.ts` does. Keycloak refuses a code twice in one 30-second window, so a scripted run with several sign-ins waits for the next window before entering the code. In agent-browser, `set headers` with `Accept-Language` did not switch the language of the web application or the Keycloak screen; the Polish screen is covered by `e2e/sign-in.spec.ts`.

Run `sh .ai/scripts/test-env-pages.sh add` in the running `trybun-test` environment instead of inserting rows by hand: it adds 55 "QA page …" records of each kind (`apps/server/prisma/qa-pages-dataset.ts`, fixed UUIDv7 IDs with the variant nibble `9`), which fill Accounts, Organizations, Projects, the members and projects of "QA page organization 01", the members and organizations of "QA page project 01", the ticket list filtered by it and the portal's My tickets of `customer@customer.example.com` (the requester of its tickets) past one page; a boot without `--reset` keeps all but the tickets (the demo restore deletes the tickets of the requester's demo organization – run `add` again); `remove` deletes exactly them (and what was added to them during the QA), and refuses, changing nothing, while a record outside them refers to one of them. - **No pointer in agent-browser** (#348, 2026-11-14): the headless Chrome of agent-browser v0.38.2 matches neither `(pointer: fine)` nor `(pointer: coarse)` (`any-pointer` too), so the compact desktop sizes behind `xl:pointer-fine:*` never apply there – the sort buttons of a table stay 44 px at 1280 px. - **Hydration checks in agent-browser** (#351, 2026-11-15): reloading in the same session serves the chunks from the browser cache, so a delay never applies (2–4 frames of a lazy boundary's fallback instead of ~100) – use a fresh `--session` per cold load. `network route` of v0.38.2 can only abort or fulfil a request, not delay it; an aborted chunk fails the whole page ("This page couldn't load"), a different scenario. To hold chunks back, run a QA-only local proxy in front of the app that delays `/_next/static/chunks/` (Auth.js cookies of `localhost` work on any port) and record the layout with `--init-script` (a `requestAnimationFrame` loop and a MutationObserver, as `e2e/hydration-layout.spec.ts` does). Commands run one at a time, so a screenshot is taken only after `open` has loaded the page – the recorded frames are the evidence of the loading window.
- **Request counts and cold loads in QA** (#359, 2026-11-17): the browser sees only the BFF, so count the API requests of a scenario per route in `.ai/qa/logs/api.log` (pino's `route` and `res.statusCode`, `grep '"req"'`), from the line count before the step. For a cold load per attempt without signing in again, save the signed-in state once (`agent-browser --session <s> state save <file>`) and open each attempt in a new session with `--state <file>`; `--init-script <file>` registers a recorder before the first navigation (e.g. a `layout-shift` `PerformanceObserver`). A `fetch` wrapper must be such an init script: `openapi-fetch` keeps the `fetch` it found when the client was created, so a wrapper added later by `eval` records nothing. Aborting a route (`network route <pattern> --abort`) fails the request as a network error, which the query retries (not a `4xx`).
