# E2E tests and the Lighthouse budget – Playwright, axe, Lighthouse

Non-obvious behaviour found when the E2E set-up was built (S0-08, October 2026, Playwright 1.64, `@axe-core/playwright` 4.14, Lighthouse 13.5). Decisions: [§2.9](../../docs/spec/02-agent-rules.md), [§2.14](../../docs/spec/02-agent-rules.md).

- **Sign-in**: `apps/web/e2e/auth.setup.ts` signs in once as the seeded Developer (password + TOTP of `docker/keycloak/dev/`) and stores the browser state for all projects. Keycloak accepts a one-time code only once, so a second sign-in in the same 30-second window fails with "Invalid authenticator code."; `SignInPage` waits for the next code. Tests must not sign out with the shared state – that ends the Keycloak session of every other test.
- The Keycloak login page has its own `banner` landmark; wait for an element of the application (the account menu) to know the sign-in completed.
- The React Compiler check (`e2e/react-compiler.spec.ts`) found no React roots through the stubbed DevTools hook on WebKit in CI (#66); it runs in the Chromium projects only.
- **WebKit** (the iPad project) needs system libraries: `playwright install --with-deps chromium webkit` (CI). On a machine without them, check the tablet project by temporarily setting `browserName: 'chromium'`.
- **axe**: exclude `[data-base-ui-focus-guard]` as in Storybook (`e2e/accessibility.ts`). Run it on an open popup only after its opening animation (`fade-in-0`, 100 ms) has finished – `AppShellPage.openedMenu()` awaits `getAnimations({ subtree: true })`; mid-fade the text is semi-transparent and `color-contrast` fails now and then (#72).
- **Lighthouse stays on 13.5** (#274, November 2026): 13.6 pulls in `sentry` (FSL-1.1-Apache-2.0, source-available) through `@sentry/node` 11, which fails the license check of Dependency review (§2.14). The maintainer kept the policy without an exception: `apps/web/package.json` has `~13.5.0` and `.github/dependabot.yml` ignores `>=13.6.0`. Lift both when an upstream release drops the dependency.
- **Lighthouse** has no Playwright integration: `e2e/lighthouse.spec.ts` starts a persistent Chromium context with `--remote-debugging-port` (Lighthouse opens its tab in the default context, which only a persistent context shares with the cookies) and calls `lighthouse(url, { port })`. Playwright's `expect` has no asymmetric numeric matchers (`expect.toBeGreaterThanOrEqual`); use `expect.soft` per metric.
- The default Lighthouse configuration is the mobile profile with simulated throttling (Lantern): the simulated LCP counts every request started before the observed LCP – also the `async` scripts in `<head>`. Client JavaScript therefore moves the LCP even when the observed LCP equals the FCP. Zod in the client bundle (≈ 60 KB gzip) pushed the shell from 2.3 s to 2.9 s; `dataOf()` imports the Problem Details parsing dynamically for that reason.
- The sign-in redirect page navigates to Keycloak at once, and Lighthouse reports the final page. Blocking `*/api/auth/signin/*` (`blockedUrlPatterns`) keeps the measurement on the page of the web application; blocking `*/api/auth/*` sends Auth.js to its error page instead. The Keycloak login screen (`keycloak.v2`) scored Performance 0.74, LCP 4.7 s (October 2026).
- `next start` warns that it "does not work" with `output: 'standalone'`, but serves the same build; the E2E web server uses it, the image runs `apps/web/server.js`.
- **Several seeded sign-ins** (S0-10): the seeded accounts share one TOTP secret, and Keycloak rejected the second account's code in the same 30-second window as "Invalid authenticator code.". The sign-ins of `auth.setup.ts` run serially with a 90-second timeout, so the wait for the next code fits. Each account has its own storage state (`storage-state.ts`).
- **Tour tests**: the developer has completed every tour (demo dataset), so tours never interrupt other tests; the newcomer's setup runs `pnpm --filter @trybun/server db:seed` first, which restores her empty tour progress. A test of one person on two devices opens its own contexts with `browser.newContext({ ...devices[…], storageState })` and runs in one project only.
- **Product tours and the LCP budget** (S0-10): adding `TourTip` (Base UI Popover and Drawer) to the shell bundle pushed the simulated LCP of the empty shell in CI to 2.59 s (budget 2.5 s; locally it still passed). The tip is loaded with `lazy()` only when a tour runs (`product-tour-step-tip.tsx`). Code that only some sessions need goes into a lazily loaded component.
- **The simulated LCP of the empty shell** (#72, October 2026): the observed LCP (the server-rendered `h1`) is at ~80 ms, and Lantern counts every request that starts before it – the whole document, CSS, preloaded fonts and all ~255 KB (gzip) of client JavaScript, ≈ 300 KB in total – plus the CPU tasks before it at 4× slowdown. The same build therefore varies in steps of ~200 ms between runs locally (whether a large script is evaluated before the first paint), in CI too (#163: `b8cf3be` gave 2659 ms and passed on a re-run). Blocking requests with `blockedUrlPatterns` does not show their weight – a blocked request stays in the graph. What moved it: preloading only the `latin` subset of Manrope (`subsets` of `next/font` are the preloaded files; `latin-ext` keeps its `@font-face` with `unicode-range` and loads for Polish letters only) and importing `next-auth/react` on sign-out – median 2.55 → 2.35 s locally. In CI it still gave 2.64 s (#71): CI lands on the upper step. What brought it to ~1.90 s locally (stable over 6 runs): loading the header menus – and Base UI's `Menu` (~57 KB gzip) with them – with `lazy()` behind a `Suspense` boundary (`lazy-user-menu.tsx`, `lazy-help-menu.tsx`, `lazy-product-tour-menu-items.tsx`). Every client module a server component imports joins the initial chunks, so the tour items passed as children of the help menu had to be lazy too; with only the menus lazy, Base UI stayed. The server still renders the menus, but on the first request of a route after a start of `next start` a lazy component suspends once and is streamed after the page: E2E tests wait with `toBeVisible()` before `boundingBox()`, and unit tests render with `prerender` of `react-dom/static` instead of `renderToStaticMarkup`, which does not wait for `Suspense`.
- **TBT and a busy runner** (#146, October 2026): the simulated TBT multiplies the main-thread tasks Lighthouse observes by the 4× CPU slowdown, so whatever else runs on the machine moves it. With `fullyParallel` the Lighthouse tests ran beside the device projects (CI: 2 workers) and failed now and then on TBT 223 ms for unchanged code. Locally the empty shell gave TBT 58–67 ms on an idle machine and 308–444 ms beside 8 busy CPU loops; the sign-in redirect 80–141 ms idle. The `lighthouse` project therefore depends on the device projects and runs with `workers: 1`. A failing device test skips the budget (`did not run`); `--project=lighthouse --no-deps` measures alone against a running environment. Since #163 every value of the budget applies to its median over three runs (§2.9, approved by the maintainer); `computeMedianRun` of Lighthouse is not used, because it picks the run by FCP and TTI, and the FCP of the shell is the same in every run.
- **The LCP steps in CI** (#163, October 2026): over 31 CI runs the simulated LCP of the empty shell landed on ~2000 ms (23), ~2450 ms (5) and 2540–2660 ms (3), at a constant FCP of 915 ms. Lantern keeps in the LCP graph every script that finished downloading before the observed LCP, unless its `EvaluateScript` started after it (`getRenderBlockingNodeData` of `@paulirish/trace_engine`); the paint of the `h1` waits for the stylesheet, which arrives with the async chunks, so on a slower runner the framework chunks – React DOM with the Next.js runtime (~72 KB gzip) and the router (~36 KB) – fall in and add ~450 or ~650 ms. The largest chunk in the graph sets the LCP, so trimming small application chunks barely moves it: an experiment moving the product tours (API client, queries, tour definitions) behind `lazy()` and Zod out of `instrumentation-client.ts` saved 12.9 KB gzip and left the local LCP at ~2020 ms (not merged). `experimental.inlineCss` made it worse (document 8 → 55 KB, LCP ~2230 ms). To see the graph, recompute `LanternLargestContentfulPaint` of `lighthouse/core/computed/metrics/` on the saved artifacts of a run (`result.artifacts`) and print the nodes of `pessimisticEstimate.nodeTimings`; `taskset -c 0` with a busy loop on the same CPU provokes the upper steps locally now and then.
- **Navigation and the LCP budget** (S0-12): reading the current account with `useQuery(currentUserQueryOptions(browserApiClient))` in the side and bottom navigation pulled the browser API client (`openapi-fetch`) into the first load of the shell and moved the simulated LCP to 2.55 s. The team layout passes `allowedActions` of its prefetched account to `AppShell` as a prop instead; only the lazily loaded menus use the query.
- **Measuring an element** (2026-10-25): `await expect(target).toBeVisible()` followed by `target.boundingBox()` is a race – the lazily loaded menus of the header (#72) and the help results, rendered again after hydration, replace the element in between, and `boundingBox()` returns `null` (the help touch-target test failed on the tablet in CI, also on `main`). Measure with `expect.poll()`, as `expectTouchTarget()` of `e2e/touch-targets.ts` does.
- **Test environment for QA skills** (S1-01; its own Compose project `trybun-test` since S1-02 – it refuses while another project publishes 5432, 6379, 8333, 8080, 3310, 8025 or 1025, e.g. `pnpm dev`; keep `-p trybun-test` when regenerating the scripts with `om-prepare-test-env`): `sh .ai/scripts/test-env-up.sh` brings up the local environment the way CI's E2E job does (Compose with the profiles `seaweedfs` and `clamav` of `.env.example`, migrations and the demo dataset, production builds of the API on 3001, the Worker – which releases uploaded attachments, S1-08 – and the web application on 3000), reuses a healthy running one in seconds, skips the build when the sources did not change, and writes `.ai/qa/test-env.json` for `om-auto-qa-pr` and `om-integration-tests`; `sh .ai/scripts/test-env-down.sh` stops only what it started (it leaves a Compose stack of `pnpm dev` that was already running). It refuses to start while `pnpm dev` serves 3000/3001. Without a `.env` it creates one from `.env.example`, which then fails two tests of `backchannel-logout/route.integration.spec.ts` in `pnpm test:coverage` (400 instead of 200; they pass alone and without the file) – delete a `.env` the script created before running the coverage suite (#139).
- **One-time codes in QA runs** (#141): `TEST_TOTP_SECRET` of `.ai/qa/test-env.env` is the Base32 form of the OTP secret (for authenticator apps and `oathtool --base32`); an HMAC over its raw bytes gives a wrong code ("Invalid authenticator code."). Decode it first, or compute the code from the raw secret as `apps/web/e2e/totp.ts` does. Keycloak refuses a code twice in one 30-second window, so a scripted run with several sign-ins waits for the next window before entering the code. In agent-browser, `set headers` with `Accept-Language` did not switch the language of the web application or the Keycloak screen; the Polish screen is covered by `e2e/sign-in.spec.ts`.
- **agent-browser on the VPS** (S1-01): Chrome for Testing aborts with "No usable sandbox" (Ubuntu blocks unprivileged user namespaces through AppArmor) and with "Socket path too long" under the long `TMPDIR` of Cezar sessions. `.ai/scripts/test-env-browser.sh` runs it with `TMPDIR=/tmp` and `--no-sandbox` (Playwright launches Chromium without the sandbox too); `agent-browser doctor` still reports its own launch test as failed, because it ignores these arguments. On 2026-11-10 (v0.38.2, #279) the script's `AGENT_BROWSER_ARGS` was not applied to a new session and Chrome failed with "No usable sandbox" again; passing `--args "--no-sandbox"` on the command line (with `TMPDIR=/tmp`) worked.
- **Invitations** (S1-03): an invited address of `customer.example.com` joins the demo organization on acceptance and breaks the member count of `organizations.spec.ts` running in parallel – the E2E invites `@example.org` (personal access). The API builds the link from `TRYBUN_DOMAIN` (`https://localhost/invitations#token=…` locally): open its path and fragment on the base URL (`InvitationPage.goto`). A new person needs a context of their own (`browser.newContext({ ...testInfo.project.use, storageState: { cookies: [], origins: [] } })`). `getByLabel` of a text that is both a radio choice card and a field label matches the radio, its hidden input and the field – use `getByRole('textbox' | 'combobox', { name })`; a dialog's accessible name follows its current title ("Add member" → "Invitation created"). `navigator.clipboard.readText()` needs `grantPermissions(['clipboard-read', 'clipboard-write'])` and is checked in Chromium only.
- **Accounts page invitations** (S1-03): GitHub sign-in is not configured in the E2E environment, so an invitation to the Administrator role (or any team target) is refused with `invitation.github_sign_in_missing` – the E2E checks that refusal and runs the flow with an end-user target. The server-rendered **Invite** button of the page opens nothing when clicked before the hydration: `AccountsPage.openInvite()` retries with `toPass()`. A pending invitation of an interrupted run stays in the project, so assertions on pending rows filter by the run's own address. The multi-device deactivation test of `accounts.spec.ts` ends Marek Manager's sessions and signs him in again, which breaks `invitations.spec.ts` (manager storage state) when both run in the full suite.
- **The tablet project is below the tablet breakpoint** (#188, 2026-11-02): `iPad (gen 11)` has a 656 × 944 viewport in portrait, narrower than `TABLET_MEDIA_QUERY` (`48rem` = 768 px), so components that switch at that breakpoint (the `TourTip` sheet, …) show their phone layout there. A test of the tablet-and-up layout skips by `page.viewportSize().width < 768`, not by project name.
- **Finding an account** (#203, 2026-11-02): `AccountsPage.find()` filled the search once; a fill before the hydration is lost (WebKit), the list stayed unfiltered, and `account('Ada Admin')` also matched the nested pending-invitation items ("Invited by Ada Admin") and their cards – 3 matches. `find()` now retries the fill with `toPass()` until the list holds a single entry, and `entries` are only the top-level cards (`:scope > li` of the list "Accounts") and the rows with a `rowheader`. Name the list and the table with `exact: true`: a role name matches a substring, and `Pending invitations of e2e-accounts-…@example.org` contains "Accounts".
- **Toasts over a bottom sheet** (#203): toasts lie above the dialogs (#172), so on the phone the "Link copied" toast covers **Done** of the sheet and takes the click; Playwright's retries keep the pointer on the toast, which pauses its timeout, so the test times out. Call `waitForToastsToClose(page)` of `e2e/toasts.ts` (moves the pointer away, then waits) before pressing a button a toast may cover – shared by the accounts and the organizations tests. Since #207 the toasts sit at the top on phones, so they no longer cover a sheet; the wait still matters on tablet and desktop (bottom right).
- **Every toast before the Danger zone** (#205, 2026-11-03): the organizations flow waited for the toasts before **Archive organization** but not after **Unarchive organization**; the "Organization unarchived" and "Organization archived" toasts intercepted **Delete organization** on desktop (CI trace) until the 90 s timeout. Wait with `waitForToastsToClose()` after every action that toasts and before the next click near the bottom right, not only before the first. Repeat it with `--repeat-each=20 --workers=1`: parallel repeats of one device share its `END_USERS` person and fail on adding the member, not on the flake.
- **Header menus before the hydration** (#206, 2026-11-03): `openHelpMenu()` retried its click since #191, `openAccountMenu()` clicked once, and the language-switch test waited the whole 30 s for the `menu` on the tablet (WebKit) in CI. Both open through `AppShellPage.openMenu()`, which repeats the click with `toPass()` until the menu shows – open a header menu only through these methods, never with `accountMenu.click()`.
- **New project before the hydration** (#236, 2026-11-05): the server renders the **New project** button of `LazyNewProjectDialog`, and a click before the hydration opens nothing – on the tablet (WebKit) in CI the next `fill` in the dialog waited the whole 30 s. `ProjectsPage.openNewProject()` and `openAddMember()` (the Add member dialog is lazy too) repeat the click with `toPass()` until the dialog shows, like `AccountsPage.openInvite()`; open these dialogs only through them. Any server-rendered trigger of a lazily loaded dialog or menu needs the same wait. `OrganizationsPage.openNewOrganization()` does the same for **New organization** of `LazyNewOrganizationDialog` (#238); the remaining `lazy-*.tsx` triggers are covered (Invite, New project, Add member, the header menus), and `LazyConfirmDialog` only lazy-loads the dialog – its button belongs to the already hydrated parent.
- **Links of a list before the hydration** (#241, 2026-11-06): the click on **Customer portal** of the Projects list landed on the tablet (WebKit) before the list's chunks had loaded and its links had hydrated (their RSC prefetches started only after it, trace of CI); no navigation followed and the page stayed on the list. `ProjectsPage.openSettings()` repeats the click with `toPass()` until the settings tabs show – open a project's settings from the list only through it. A server-rendered link followed by an expectation of the next page needs the same wait.
- **End users in the E2E tests** (S1-09): the customer (`customer@customer.example.com`, one project) and the partner (`partner@customer.example.com`, two projects) of the demo dataset sign in with the password only (`SignInPage.signInWithPassword`, `CUSTOMER_STORAGE_STATE`, `PARTNER_STORAGE_STATE`); a test that changes a shared demo ticket (the resolution answer of "Cannot change my password") runs on one device only, because the three device projects run in parallel. The two Keycloak users are in `docker/keycloak/dev/trybun-realm.json`; an existing local realm needs them added with `partialImport` (`keycloak.md`). The demo organization now has 8 members (`organizations.spec.ts`). Do not start the local environment on the agents' VPS while the `trybun-test` project of the QA skills runs – it uses the same ports; the CI run is the E2E evidence then.
- **Attachments in the E2E tests** (S1-08): uploads need SeaweedFS and ClamAV (the `seaweedfs,clamav` profiles of `.env.example`, also in CI) and the Worker, which `playwright.config.ts` starts as a web server without a URL (nothing is awaited). The Worker scans a 1-pixel PNG in a few seconds; the view polls 3 s, 6 s, 12 s…, so the inline image is awaited for up to 60 s (`test.slow()`). Choose files with the `filechooser` of **Attach files** (`PortalPage.addFiles()`, repeated until the dialog opens). A test that leaves drafts eats the end user's draft quota (50) across runs – submit the form instead. The demo dataset deletes the attachments of the tickets it removes (`RESTRICT` of `attachments.ticket_id`), else `pnpm db:seed` of the newcomer's setup fails after a run with files.
- **The `trybun-test` environment drifts** (2026-11-06): the end users' password there had been changed from `trybun` ("Invalid username or password" in `auth.setup.ts`); it was reset through the Admin API with the realm `passwordPolicy` lifted for the call and restored right after. About 40 `@example.org` accounts left by earlier runs push **Marek Manager** off the first page of Accounts, which fails `accounts.spec.ts` (and the Administrator-panel tour test) locally; CI starts with an empty database.
- **Account language against browser language** (S1-10, 2026-11-08): the demo team accounts speak Polish (`language: 'pl'`, demo dataset) while the stored states have no language cookie, so the pages are English but whatever follows the *account* language – the description templates of the full form (`/tickets/new`) – is Polish. `settings.spec.ts` switches the developer to English for a moment in parallel, so a test of the developer's templates reads the language the form inserted (`TicketFormPage.insertedLanguage()`); the fixed Polish check uses the Project manager, whose language no test changes.
- **One ticket per test and device** (S1-10, PR #256 review): `fullyParallel` runs the tests of a file in parallel too, not only the device projects – two tests that picked the same unassigned ticket per device raced (one assigned it while the other expected **Unassigned**, and each `finally` unassigned under the other). `UNASSIGNED_TICKETS` of `tickets.spec.ts` gives every test×device its own unassigned demo ticket that no other test reads; a new test that changes a demo ticket takes one of its own the same way.
- **Axe right after a submit** (S1-13, PR #270): `Button` has `transition-all` and `disabled:opacity-50`, and a form's submit is disabled until its mutation's invalidations have been read again. The comment form's note appeared before the ticket was read again (two requests since S1-13 resolve the identifier, then read the detail), so axe ran while the button faded back and reported `color-contrast` on the tablet now and then. Before axe after a submit, wait until the button is enabled and its animations have finished (`element.getAnimations()`, as `comments.spec.ts`).
- **The tablet project misses the narrowest tablet and Polish** (2026-11-10, PR #294 review): the `tablet` project is an iPad at 820 px in English, so a table that fits there can still scroll sideways at 768 px (`md`) in Polish, where labels are longer („Funkcjonalność”, „Zaktualizowano”, „Oczekuje na zgłaszającego”). Check width-sensitive layouts with `test.use({ locale: 'pl-PL', viewport: { width: 768, height: 1024 } })` in the tablet project (`ticket-list.spec.ts`); `locale` switches the language because the stored states carry no `NEXT_LOCALE` cookie. On main the custom ticket view already scrolls by about 50 px at 768 px in Polish – #295 extends the layout checks to every locale.
