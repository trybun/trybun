# Prisma ORM 7 – pitfalls

Non-obvious behaviour of Prisma found when the version was chosen (October 2026). Decision: [§14.2](../../docs/spec/14-architecture.md), [§14.5](../../docs/spec/14-architecture.md); patterns: [§18.3](../../docs/spec/18-code-patterns.md).

- `prisma@latest` installs the **Prisma ORM 8 release candidate**; Prisma ORM 7 is the `prev` tag. Install and update with an explicit major: `prisma@7`, `@prisma/client@7`, `@prisma/adapter-pg@7`.
- Prisma ORM 8 is a different architecture (CLI plus `@prisma/orm-postgres`, a "contract" instead of `schema.prisma`) without `$extends`, atomic `increment`, transaction isolation levels and `P2002`-style error codes. Prisma 7 and 8 can run side by side on one database, so the later move can go query by query.
- Prisma 7: driver adapters are mandatory (`new PrismaClient({ adapter: new PrismaPg({ connectionString }) })`); configuration lives in `prisma.config.ts`; `.env` is not loaded automatically; the `prisma-client` generator needs an `output` path; `migrate dev` no longer runs `generate` or the seed.
- Partial indexes (`@@index([…], where: raw("…"))`) are a preview feature in Prisma ORM 7.10 (`partialIndexes`, P1012 without it), and an index created only in migration SQL would be dropped by the next generated migration – the project uses neither (S0-21). A trigger that allows exactly one column change compares the rows without it: `to_jsonb(NEW) - 'col' = to_jsonb(OLD) - 'col'`, which also covers columns added later (S0-21, the IP expiry of the audit log).
- A PostgreSQL error raised by a trigger with `ERRCODE = 'restrict_violation'` reaches Prisma Client as "Foreign key constraint violated on the (not available)", without the message; a plain `RAISE EXCEPTION` (`P0001`) keeps it (S0-14, the immutable audit log).
- `$use` middleware is removed – cross-cutting behaviour uses client extensions (`$extends`). `@casl/prisma` 2.x requires `$extends(createCaslExtension())`; with the `prisma-client` generator its runtime (`@casl/prisma/runtime`) is wrapped with the project's generated types.
- TypedSQL (`$queryRawTyped`) is still a preview feature – the project uses `$queryRaw` tagged templates ([§18.3](../../docs/spec/18-code-patterns.md)).
- Interactive transactions: `$transaction(async (tx) => …, { maxWait, timeout, isolationLevel })`; since 7.5 a nested `$transaction` uses a savepoint.
- `@default(uuid(7))` generates UUIDv7 in Prisma Client (application side), as [§17.2](../../docs/spec/17-conventions.md) requires.

Found when Prisma was set up (S0-04, October 2026):

- The lockfile of Prisma 7.10 contains `@prisma/engines-version@8.1.0-…` – an engine build identifier, not a Prisma ORM 8 package; `scripts/check-prisma.js` exempts it.
- `@prisma/engines` and `prisma` need their install scripts (`allowBuilds`): the schema engine of the migrations is a downloaded binary. `prisma` is a production dependency of `apps/server`, because the image runs `prisma migrate deploy` (one-off `migrate` service).
- `prisma generate` runs without `DATABASE_URL` (postinstall, CI, image build) as long as `prisma.config.ts` does not call `env()`, which throws for a missing variable. `prisma migrate diff --from-empty --to-schema …` still needs a datasource URL (any URL; nothing connects) – without one it fails with an empty "Error in Schema engine". With `--script` it may also print nothing and exit 0 (S0-10, also with `--from-schema <old schema>`); a new migration is easiest created with `prisma migrate dev --create-only --name <name>` against a temporary database (the project image `trybun-postgres-test` needs `KEYCLOAK_DB_PASSWORD`), then renamed to the timestamp pattern of the folder.
- The seed (`migrations.seed`) runs with `tsx`: Node's type stripping cannot run the generated client imported with `.js` extensions. `tsx` works without the install script of `esbuild` (denied).
- The generated `prisma-client` output (`src/generated/prisma`) is TypeScript; the server bundle inlines it, its runtime `@prisma/client/runtime/*` stays external.

Found when projects were built (S1-01, October 2026):

- **`@casl/prisma` on `PrismaService`**: the client is a class (`PrismaService extends PrismaClient`), so its constructor returns `this.$extends(createCaslExtension()) as unknown as this`; Nest then injects the extended client, which delegates to the base one, so `onModuleDestroy` still runs. The ability is `Ability<[string, AppSubject], PrismaQueryOf<Prisma.TypeMap>>` built with `createPrismaAbility` of `@casl/prisma/runtime`; `accessibleBy(ability, action).ofType('Project')` gives a typed `WhereInput`. A record type of `Subjects<…>` must be a type alias (`type X = { … }`), not an interface or a Prisma payload type, because `Subjects` requires an index signature. `ability.relevantRuleFor(action, subject(…))?.reason` returns the reason of a denying `cannot(…).because(code)`.
- **To-one relations in CASL conditions** (S1-03): the in-memory check of `can(action, subject(…))` throws `"equals" does not supports comparison of arrays and objects` for a nested to-one condition written as in Prisma's shorthand (`project: { members: { some: … } }`); write it with `is` (`project: { is: { members: { some: … } } }`), which both the in-memory check and `accessibleBy` accept. A record whose relation is `null` then simply does not match.
- **Generic CASL filters** (S1-04): `accessibleBy(ability, 'read').ofType(subject)` with a type parameter `S` for the subject gives a type TypeScript cannot relate to `Prisma.<Model>WhereInput`; `PrismaRecordAccess` names it once with `as RecordFilters[S]` instead of a `switch` per model. A union of subject records must be distributive (`S extends RecordSubject ? RuleRecords[S] & ForcedSubject<S> : never`) to be accepted by `ability.can()`. Nested relation conditions (`organizations: { some: { organization: { is: { state, members: { some } } } } }`) work in memory as long as the record carries the relation, limited like the condition; `ability-definitions.spec.ts` fails when a descriptor's `select` misses a field a condition reads.
- **`scripts/check-prisma.js` parses a model block up to its first `}`**: a `{` `}` in a `///` comment of the schema (e.g. a regex `{1,9}`) cuts the block and reports a missing `@@map`. Keep braces out of schema comments.
- **`prisma migrate diff` in Prisma 7 has no `--shadow-database-url`**: apply the existing migrations to a temporary database (`DATABASE_URL=… prisma migrate deploy`), then `prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script`; `--exit-code` (0 = no drift) checks a hand-written migration.

Found when organizations were built (S1-02, October 2026):

- **Which unique index a `P2002` violated**: with the driver adapter, `error.meta` has no `target`; the index is in `meta.driverAdapterError.cause.constraint.index` (e.g. `organizations_name_lower_key`). `isUniqueViolation(error, index)` of `platform/database` reads it, for a model with several unique rules.
- **A unique index on an expression** (`CREATE UNIQUE INDEX … ON "organizations"(lower("name"))`) written in the migration SQL is ignored by `prisma migrate diff`: the drift check (`--exit-code`) stays 0 and the next generated migration does not drop it, unlike a partial index.
- **Case-insensitive equality** in Prisma (`mode: 'insensitive'`) compiles to `ILIKE`, where `_` and `%` are wildcards – compare e-mail addresses and names with `lower(…) = lower(…)` in `<feature>.sql.ts` instead (`organizations.sql.ts`).
Found when tickets were built (S1-05, November 2026):

- **A restricting foreign key (`P2003`)** reports its constraint like a unique index: `meta.driverAdapterError.cause.constraint.index` holds the constraint name (e.g. `tickets_organization_id_fkey`, `kind: RestrictViolation`); `isForeignKeyViolation(error, constraint)` reads it (S1-05).
- **`activity_events` is immutable** (S1-05): its triggers refuse every `UPDATE`, every `TRUNCATE` and every `DELETE` while the event's ticket exists, so tests and the demo dataset never clean it up directly – they delete the tickets, whose deletion cascades to their events. The demo dataset deletes the tickets of the demo projects and of the demo organization before the organization, which the restricting foreign key of the ticket snapshot would keep.

Found when ticket statuses were built (S1-06, November 2026):

- **Prisma queries are lazy**: `prisma.x.delete(...)` returns a `PrismaPromise` that runs only once it is awaited or `then` is called. A race test that starts a query on another connection and waits for it in `pg_stat_activity` must call `.then((row) => row)` on it first, or the query never starts and the wait times out.
- **Deleting an original and its duplicate in one statement** fails on the restricting foreign key `ticket_relations_target_ticket_id_fkey`, even with `ON DELETE NO ACTION` – the cascade from the duplicate does not run before the check. Delete the relations first (the demo dataset does).
- **Check constraints across columns** keep status-dependent fields consistent (`tickets_waiting_fields`, `tickets_closed_at_terminal`, `tickets_rejection_reason_rejected`); the test factory `createTicket` fills the fields a status requires, so tests that create a `waiting_for_requester`, terminal or `rejected` ticket pass only the status.
