# Internationalization – next-intl, intl-messageformat, Keycloak messages

Non-obvious behaviour found when the i18n infrastructure was built (S0-06, October 2026, `next-intl` 4.14, `intl-messageformat` 12, Keycloak 26.8). Decisions: [§13.1](../../docs/spec/13-non-functional.md), [§18.5](../../docs/spec/18-code-patterns.md).

## next-intl 4 without i18n routing

- The request configuration (`apps/web/src/lib/i18n/request.ts`) is passed to `createNextIntlPlugin()` and must be the file's default export (lint exception in `@trybun/eslint-config/nextjs`).
- `NextIntlClientProvider` rendered in a Server Component inherits locale, messages and time zone of the request for every prop not passed. Passed `messages` replace those of a parent provider – nested providers do not merge (`NextIntlClientProviderServer`, next-intl 4.14) – so every set of `CLIENT_NAMESPACES` repeats the namespaces of its parents (#139). In unit tests a layout calling `getMessages()` needs it in the `next-intl/server` mock.
- **Vitest resolves the client build** of `next-intl` (no `react-server` condition): `getRequestConfig`, `getLocale` and `getTranslations` throw "not supported in Client Components". Tests mock `next-intl/server` (`getRequestConfig: (create) => create`, which is what the server build does).
- Typed keys: `declare module 'next-intl' { interface AppConfig { Locale; Messages } }` (`lib/i18n/next-intl.d.ts`) – `t('unknown')` fails `tsc`.
- `next-intl` pulls `@parcel/watcher` (its message extractor) with an install script that only builds from source when no prebuilt binary fits; denied in `allowBuilds`.
- `next-intl` depends on `intl-messageformat` 11 while the server uses 12; both parse the same ICU syntax.
- Setting a cookie in a Server Action already re-renders the page; `changeLanguage` also calls `refresh()` from `next/cache` to make it explicit.

## Catalogues

- TypeScript `nodenext` requires `with { type: 'json' }` on JSON imports; Turbopack, rspack (server bundle) and Vitest all accept it, and the catalogues are inlined into the bundles.
- `CATALOGUES = { en, pl } satisfies Record<string, Messages>` makes a key missing from `pl.json` a type error; extra keys and malformed ICU are caught by `catalogues.spec.ts`.
- Polish number format does not group four-digit numbers (`1234,5`, but `12 345`): the CLDR minimum grouping digits, not a bug.

## Keycloak login theme

- Keycloak formats its messages with **Java `MessageFormat`**: a literal `'` must be doubled and arguments are positional (`{0}`). The generator (`packages/i18n/scripts/generate-keycloak-theme.js`) converts ICU text and rejects named arguments, plurals and tags.
- Properties are written ASCII-only with `\uXXXX` escapes, which every Keycloak version reads regardless of the file encoding.
- Language of the login screen: `ui_locales` of the authorization request comes before `Accept-Language` and the realm's `defaultLocale` (checked by `realm.integration.spec.ts`); a language picked on the Keycloak screen (`kc_locale`, `KEYCLOAK_LOCALE` cookie) or a user's `locale` attribute can take precedence over `ui_locales` (Keycloak's `DefaultLocaleSelectorProvider`; not verified). Auth.js passes `ui_locales` as the third argument of `signIn()` (authorization parameters).
- The heading of the `keycloak.v2` login page is `loginAccountTitle`; the theme `trybun` (`parent=keycloak.v2`) overrides only the keys of the `keycloak` namespace. Themes are read from `/opt/keycloak/themes/<name>` (bind mount in Compose, copied into the Testcontainers container) and selected with `loginTheme` in the realm.
- Turborepo ignores files outside a package unless the package's `turbo.json` lists them with `$TURBO_ROOT$/…`; `packages/i18n/turbo.json` adds the generated theme to the inputs of `lint` and `build`.
- A test that renders `NextIntlClientProvider` with an `onError` that throws must pass `timeZone`: without it `onError` receives `ENVIRONMENT_FALLBACK`, and the first render fails with a misleading "context from `NextIntlClientProvider` was not found".
