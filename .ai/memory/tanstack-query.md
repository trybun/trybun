# TanStack Query – mutations and infinite queries: callbacks, unmounting, offline, failed pages

Non-obvious behaviour of TanStack Query 5 found while fixing #368 (PR #387). Patterns: [§18.5](../../docs/spec/18-code-patterns.md).

- **Per-call callbacks of `mutate` never run for an unmounted component.** `mutate(variables, { onSuccess, onError })` calls them only while the observer still has listeners (`mutationObserver.ts`, `hasListeners()`). The hook-level `onSettled` runs first and is awaited, so an invalidation there (`invalidateQueries`) can refresh a list that removes the very component before the per-call `onError` runs. The toast of that refusal is then silently lost. Typical case: the last item of a list whose wrapper renders nothing when the list is empty. Use `mutateAsync(variables).then(onSuccess, onError)` for feedback that must survive the component, as `pending-invitation-list.tsx` does. A component test only catches it when another query of the invalidation is still running after the list has gone (`inviting-flows.spec.tsx`, `ProjectInvitations`).
- **Offline pauses mutations instead of failing them.** With the default `networkMode: 'online'`, a mutation started while `navigator.onLine` is false waits and is sent once the browser is back online. The DevTools Offline switch (or `context.setOffline`) therefore never reaches an error path. To test an error, block or abort the request URL instead (Playwright `page.route(…).abort()`; Chrome and Edge DevTools **Request conditions** with a URLPattern such as `http://localhost:3000/api/v1/invitations/*/revocation`).
- **A failed later page sets `isError` and keeps `data`** (found in #434, TanStack Query 5.107). After `fetchNextPage()` fails, an infinite query has `status: 'error'`, `isError: true`, `isFetchNextPageError: true` and all the pages loaded before; a refetch error keeps `data` too (`isRefetchError`). A list that checks `isError` before its rows therefore drops what it already showed. Replace the rows only on `isLoadingError` (error without data) and show the other errors above **Load more** ([§18.5](../../docs/spec/18-code-patterns.md)). In a server-HTML test seed that state with `seedFailedLaterPage()` of `apps/web/test/query-state.ts`; in jsdom press **Load more** against `laterPagesFail()` of `test/dom/fake-api-client.ts` instead, because the seeded data is stale and a mounted query reads it again (`refetchOnMount`). While **Load more** reads the page again, the query stays in `error` with the old error: hide the alert while `isFetchingNextPage`, so that a second failure mounts it again and is announced.
- **Observer notifications in DOM tests run inside `act()`, set once in `test/setup/query-notifications.ts`** (#496, 2026-11-24; replaces the `act()` note of the review of PR #470). `await client.refetchQueries(...)` resolves when the cache holds the new state, but `notifyManager` notifies the observers in a batch scheduled with `setTimeout(0)`. `await act(() => client.refetchQueries(...))` alone does **not** settle it: the batch may run after `act()` returns, so the check sees the old render – a component test of a gone ticket then failed 4 of 15 fresh runs when it checked an effect (`router.refresh()`), and a test of a ticket that must stay shown passed even with the component broken when the batch was late. The set-up file of the `web` unit project therefore sets `notifyManager.setScheduler(queueMicrotask)` and `setNotifyFunction((callback) => act(callback))` in the jsdom environment, the two settings the `notifyManager` documentation names for tests. With it, `await act(() => client.refetchQueries({ queryKey }))` and then the check is deterministic: 20 of 20 runs pass, and 20 of 20 fail with the component or the hook broken. Never add a wait of some milliseconds, and never change the scheduler in a single test (`team-views.spec.tsx`, `portal-views.spec.tsx`).
- **Never read the next page from an effect** (#471, #473, TanStack Query 5.107). After a failed `fetchNextPage()` the query keeps `hasNextPage` and `isFetchingNextPage` turns false again, so an effect on `hasNextPage && !isFetchingNextPage` asks for the failed page again at once, without end: about 3,500 refused reads in 15 s in the QA of PR #470, which used up the person's rate limit. Stopping on `isFetchNextPageError` is not enough. A failed query is invalidated, so every window focus or remount starts it again whatever its `staleTime`, so a failed page costs two more reads at each, and a successful refetch reads every loaded page again. Pickers search on the server instead (first page only, §18.5), and a whole bounded list uses `allPageItems`.
