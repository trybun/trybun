# shadcn/ui – primitives, CLI and class merging

Non-obvious behaviour of shadcn/ui found when the primitives were chosen (October 2026). Decision: [§14.2](../../docs/spec/14-architecture.md), [§14.5](../../docs/spec/14-architecture.md); patterns: [§18.6](../../docs/spec/18-code-patterns.md).

- Since July 2026 `shadcn init` uses Base UI by default; `-b radix` selects Radix and `--base aria` React Aria. Registry items without a `registry:base` configuration initialize as Base UI. Documentation pages exist per base (`/docs/components/base/…`, `/docs/components/radix/…`) – use the `base` ones.
- The Radix flavour of `Drawer` is built on `vaul`, which is unmaintained; the Base UI flavour uses the Drawer of Base UI (`swipeDirection`). Vaul-only props such as `repositionInputs` have no one-to-one replacement.
- `Command` uses `cmdk` in every flavour. `Toast` (July 2026) exists only for Base UI.
- Radix → Base UI: `asChild` becomes `render`; examples and agents' habits from older shadcn/ui code use `asChild`.
- Since September 2026 `shadcn init` installs the `cn` package (shadcn-ui/cn, no dependencies) instead of `clsx` + `tailwind-merge`; `lib/utils.ts` only re-exports it, and registry components import `cn` directly. Custom class groups are configured with `cn/config` (`extend`, `override`, `prefix`, like `extendTailwindMerge`). `shadcn migrate cn` converts existing code.
- In a monorepo every workspace has its own `components.json`; `style`, `iconLibrary` and `baseColor` must match, and `tailwind.config` is `""` for Tailwind 4. The ui package exports `./globals.css`, `./components/*`, `./lib/*` and `./hooks/*`; components are flat in `src/components/` (no `ui/` subfolder).

## Set-up and adaptation (S0-07, shadcn 4.22, Base UI 1.9)

- `shadcn add` in `packages/ui` fails with "Could not resolve the following aliases" until the aliases resolve: the package `exports` (`./components/*`, `./lib/*`, `./hooks/*`) are enough, no `paths` in `tsconfig.json`. Components import each other through the package name (`@trybun/ui/components/button`); TypeScript and Vite resolve it as a self-reference.
- The CLI installed only `@base-ui/react` and `cn`; `class-variance-authority`, `lucide-react`, `tw-animate-css` and `shadcn` (for `shadcn/tailwind.css`, which defines the `data-open`/`data-closed` variants) had to be added by hand.
- `shadcn init -p` takes the preset names `nova`, `vega`, … (the style becomes `base-nova`); `base-nova` itself is rejected.
- base-nova components use arbitrary values (`text-[0.8rem]`, `rounded-[min(var(--radius-md),10px)]`, `ring-[3px]`, `min-w-[96px]`), Tailwind palette colours (`bg-black/10`) and focus rings at 50 % opacity (below 3:1); the adapted components replace them with tokens. The Drawer and Toast motion relies on CSS variables of Base UI in arbitrary properties – the lint rule of `@trybun/eslint-config/tailwind` allows variable references for that.
- `cn` (like tailwind-merge) treats an unknown `text-*` class as a colour: `cn('text-body', 'text-success')` drops `text-body`. Custom font-size tokens therefore need `createCn` of `cn/config` – and the registry components import `cn` from `cn` directly, so the configured instance would have to replace those imports. The theme keeps Tailwind's type scale, which `cn` knows.
- Base UI `Toast.Close` is `aria-hidden` until the toasts are expanded (hover, focus; F6 from the keyboard). Testing Library gives aria-hidden elements an empty accessible name even with `hidden: true` – query it with `getByLabelText`.
- **Focus ring colour** (#177): `--ring` is the interactive Blue (`--link`, `--info` share it), never a red close to `--destructive` and not Ink, which reads as black (#183). The indicator is 2 px: a bordered control uses `focus-visible:border-ring focus-visible:ring-1`, a borderless one `focus-visible:ring-2`, a filled one (default and destructive Button, default Badge, Switch, Radio, the initials of the account menu) `focus-visible:ring-2 focus-visible:ring-offset-2 focus-visible:ring-offset-background`, so the ring keeps a gap from the fill. A radio inside a choice card drops its own ring with important card rules (`group-has-[:focus-visible]/field-label:ring-0!`): the `:where()` group selector is weaker than `focus-visible:*`, so without `!` both the card and the radio showed a ring. An invalid control has only `aria-invalid:border-destructive` at rest and `aria-invalid:focus-visible:ring-destructive` on focus – a permanent `aria-invalid:ring-*` made every invalid field look focused. The `aria-invalid:*` classes come after `focus-visible:*`, so a focused invalid field keeps its danger border. A scrolling list (`overflow-*-auto`) clips the ring of its items: give it `p-1` with `-m-1` (and `w-auto` on a `w-full` element) so the 3 px ring fits, as the candidate list of `add-member-dialog.tsx` does. A story that reads computed `border-color` or `box-shadow` after focus passes `className: 'transition-none'`: `transition-colors` / `transition-all` otherwise return the starting value.
- **Global attribute styles against utilities** (#186): a rule in `@layer components` loses to every utility of the element, whatever its specificity – the tour ring `[data-tour-highlighted]` vanished on `Button` targets because of their `outline-none`. A style that must win over a component's utilities goes into `@layer utilities` after the Tailwind import (equal specificity, later source); a default the element may override (the shape) stays in `components`. `outline-none` also sets `--tw-outline-style: none`, which `outline-<width>` reads, so such a ring sets `outline-solid` explicitly.
- **Scrolling to an element with an outside ring** (#191): `scrollIntoView({ block: 'nearest' })` aligns the **border box** with the viewport edge, so an outline drawn outside it (the 5 px tour ring) ends cut off, and the sticky header or the fixed bottom navigation of phones covers the element. Give the element a scroll margin (`[data-tour-highlighted]`: `scroll-mt-18`, `scroll-mb-safe-offset-19`, `md:scroll-mb-4`) and judge "at the edge" by where it lands after the scroll, not by its box before it (`isRingInset` of `product-tour.ts`).
- Base UI focus guards (`[data-base-ui-focus-guard]`, `aria-hidden` with `tabindex="0"`) make axe report `aria-hidden-focus` after a menu closes; the Storybook a11y context excludes them.
- **Padding of a Drawer** (#190): the `className` of `DrawerContent` lands on the outer `drawer-popup`, while the children sit in the inner `drawer-content`, which has `overflow-hidden` and no padding – padding or `gap` passed to `DrawerContent` does not space the children, and an action at the edge loses its focus ring (4 px for `default`: `ring-2` + `ring-offset-2`). Pad a wrapper inside it (`DrawerHeader`/`DrawerFooter`, or `tour-tip-body` of `TourTip`); the swipe handle already spaces the edge next to it. A story measures the actions against `[data-slot="drawer-content"]`.
- The Drawer swipes on touch events and on pointer events of other pointer types. A swipe-to-close test dispatches `TouchEvent`s (`touchstart`, ten `touchmove` 16 ms apart, `touchend`) on the popup (`drawer.stories.tsx`).
- **Popover anchored to any element** (S0-10): `Popover.Positioner` takes `anchor` (an element, a ref, a virtual element with `getBoundingClientRect`, or a function returning one); `PopoverContent` passes it through. Base UI resolves a *function* anchor only once while the popup stays open (it keeps the function in a stable callback), so a new function never moves an open popup – `TourTip` turns it into a virtual element (`getBoundingClientRect` + `contextElement`) memoized on the function, whose new identity re-registers the anchor (#188). A non-modal Popover or Drawer closes on `outside-press` and `focus-out` too – `TourTip` accepts only `escape-key`, `close-press`, `close-watcher` and `swipe` from `onOpenChange`. Popups animate in from `opacity: 0`, so a story asserts `toBeVisible()` inside `waitFor`. `Menu.LinkItem` is the menu item for navigation (`DropdownMenuLinkItem`, `render={<Link …/>}`).
- **Field on Base UI** (S0-12): `@trybun/ui` builds the shadcn `Field` family on Base UI `Field` parts, so `FieldLabel`, `FieldDescription` and `FieldError` link to the control (`Input` is a Base UI `Field.Control`) without hand-written IDs. Base UI `Field.Label`/`Description`/`Error` throw "FieldRootContext is missing" outside `Field.Root` (the components fall back to plain elements there); `Field.Error` must be controlled (`match`) by the form library – React Hook Form sets `invalid` on `Field` and passes `errors` to `FieldError`. Text colour set on the `Field` cascades into the input (dark-mode contrast in axe), so the invalid colour sits on `FieldLabel`. `disabled` on a `Field` does not disable the toggle of `PasswordInput` – pass it to `PasswordInput`.
- **Tabs** (S1-01): the panel of the previous tab stays in the document until its exit transition ends, so right after a tab change there are two `tabpanel`s – a story or test waits with `waitFor(() => expect(canvas.getByRole('tabpanel')).toHaveTextContent(…))`. Only the active `TabsContent` mounts its children.
- **Toasts in the app** (S1-01): `LazyToaster` (`features/app-shell/components/lazy-toaster.tsx`) mounts the `Toaster` of `@trybun/ui` after the first paint in the layout of the views that show toasts (`app/(team)/projects/layout.tsx`), never in the team layout: there its chunk loads on every page, and after #134 it broke the Lighthouse budget of the empty shell on CI (TBT 249–287 ms, LCP 2523 ms); components add messages with `toast.add({ title, type, actionProps: { children, onClick } })` of `@trybun/ui/components/toast` (e.g. Undo of archiving).
- **Toasts above overlays** (#172): dialogs, drawers and popups of `@trybun/ui` sit at `z-50`, and at one layer the later portal wins – a dialog opened after the lazily mounted toaster covered its toasts (on phones the bottom sheet lies right over them). `ToastViewport` is therefore `z-60`; a new overlay stays at `z-50`. Toasts stay `aria-live`, so `markOthers` of a modal dialog never hides them from screen readers, and a press on a toast does not close the dialog (`AboveDialogOnPhone` of `toast.stories.tsx`).
- **Toasts before the toaster mounts** (S1-10, 2026-11-08): Base UI's `createToastManager()` emits `add` only to the providers subscribed at that moment, so a toast added before `LazyToaster` mounted vanished – in CI, "Assigned to …" with **Undo** of a bottom sheet on the phone, whose trace showed no toast portal in `<body>` until seconds later. `toast` and `createToastManager` of `@trybun/ui` now queue such toasts and `Toaster` adds them after its provider subscribed (the effect of the parent runs after the child's); one older than 10 s is dropped (`AddedBeforeTheToaster` of `toast.stories.tsx`).
- **Toasts at the top on phones** (#207, 2026-11-03): at the bottom, the toasts above the sheets (#172) covered the actions of a bottom sheet ("Link copied" over **Done**). Below `md` – the breakpoint of the bottom sheets – `ToastViewport` sits at `top-18` (below the `h-14` header) and the stack grows downwards; from `md` on, at the bottom right. One set of motion classes serves both: `--stack` (`1` down, `-1` up) multiplies the offsets, the peek and the enter/exit translation; `swipeDirection` follows `useMediaQuery(TABLET_MEDIA_QUERY)` (`up`/`right` on phones, `down`/`right` from `md`).
- **Radio group** (S1-01 review): an `after:` hit area is positioned inside the border, so a 16 px bordered radio needs `after:-inset-4` (46 px), not `-inset-3.5` (42 px), for 44 px; the story measures `::after`. A picker of records is a `RadioGroup` of choice cards (`FieldLabel` around a horizontal `Field`); the label makes the card the hit area and the accessible name of the radio.
- **Outline buttons on coloured surfaces** (S1-02 QA, #149): the base-nova `outline` variant set no text colour of its own, so inside `Alert variant="warning"` (`text-warning-foreground`, white) its label became white on white; it now sets `text-foreground`. In the dark theme its background is translucent (`dark:bg-input/30`) and takes the colour of the surface – an action on a coloured alert uses the opaque `secondary` variant. `DialogTitle` breaks long words (`wrap-anywhere`): an e-mail address in a title widened the bottom sheet past a 360 px phone.
- **Combobox clearing** (#161): in single selection, clearing the text of `ComboboxInput` sets the value of Base UI's `Combobox` to `null` (`onValueChange(null)`), so a nullable field (the time zone of Account settings, `null` = system default) needs no extra clear button; `account-components.spec.tsx` covers it.
- **Combobox searched on the server** (S1-10, 2026-11-08): with a controlled `value` whose item stays selected, typing into `ComboboxInput` starts from the selected label ("Unassigned" + "ja" → "Unassignedja"), and ignoring the `null` of a cleared input makes Base UI write the label back. Pass `filter={null}`, control `inputValue` (the search while open, the label while closed) and take the search from `onInputValueChange` only for the reasons `input-change` and `input-clear` – an item press also writes the label (`assignee-control.tsx`).
- **Combobox with the input in the popup** (#279 Phase 2, 2026-11-10): with `ComboboxPopupInput` inside `ComboboxContent`, Base UI gives `ComboboxTrigger` the `combobox` role (`aria-haspopup="dialog"`), which takes no name from its content – axe `button-name` fails without an `aria-label` (keep the visible text in it, WCAG 2.5.3); tests find it by role `combobox`. The popup becomes a `dialog` that needs a name (`aria-label` on `ComboboxContent`) – axe does not report it, `aria-dialog-name` is a best-practice rule outside the tags of the story tests. Loading and "type to find more" go into `ComboboxStatus` (Base UI's live region, kept mounted), not a `role="status"` mounted together with its text – and never `display: none` while empty (no `empty:hidden`, which the base-nova `ComboboxEmpty` uses): a hidden region leaves the accessibility tree and its first text arrives with it; story `Picker` checks it. The input gets the focus on a mouse or keyboard open (on touch the popup does, so the on-screen keyboard stays down), Home/End move the highlight to the first/last option, Esc returns the focus to the trigger, and in `multiple` mode Enter toggles and keeps the popup open. Base UI writes `data-selected=""` on items, but the `data-selected` variant of `shadcn/tailwind.css` matches only `[data-selected="true"]` – style a chosen item with `aria-selected:` (`ComboboxCheckboxItem`). The popup zooms in on open: measure sizes and `toBeVisible` inside `waitFor`; a closing popup still counts as visible while it fades, so assert "still open" by `aria-expanded` of the trigger.
- **ScrollFade** (#167): the fade of a sideways-scrolling bar follows a `ResizeObserver` on the bar **and every element in it** – the bar itself keeps its width when a label grows after a language switch or a late font load, and so does a block-level `ul` inside it; items added later are observed through a `MutationObserver`. Its state changes after the `scroll` event, so a story waits for a fade with `waitFor`. A fade alone was invisible when the edge fell into the gap between two items (QA of #171), so every edge carries an arrow (`aria-hidden`, `tabIndex={-1}`, 44 px); and Chrome showed the bar's horizontal scroll bar until the first scroll, over the mark of the current item, so `ScrollFade` hides it (`*:[scrollbar-width:none]`).
- **Tooltip** (#217, Base UI 1.9): the popup has no role and Base UI sets no `aria-describedby` on the trigger, so a tooltip is visual only – the trigger needs its own accessible name, and tests find the popup by `[data-slot="tooltip-content"]` (E2E: `AppShellPage.navigationTooltip()`). It opens on hover after 600 ms (`OPEN_DELAY`; a `TooltipProvider` makes neighbours open at once) and at once on keyboard focus – also in jsdom with `userEvent.tab()`. In jsdom no CSS applies, so elements hidden per breakpoint (`xl:hidden`, `hidden xl:inline-flex`) stay focusable; tab until the target has focus instead of counting tabs. `disabled` on `Tooltip` keeps it closed – better than hiding it with CSS, which would still catch hover and focus.
- **Toast actions close their toast** (S1-10 QA, 2026-11-08): Base UI's `Toast.Action` runs `actionProps.onClick` and leaves the toast open, so **Undo** stayed pressable until the timeout. `ToastList` of `toast.tsx` passes `onClick={() => close(id)}` (merged with `actionProps`, both run) and `disabled` while `transitionStatus === 'ending'` – the button stays in the DOM for the exit motion and a double click would otherwise press it again. In jsdom the exit motion never ends: a test sees `data-ending-style` on the toast and a disabled action, not a removed toast (`undo-toast.spec.tsx`; story `ActionClosesTheToast`).
- **Checkbox next to a sort button in a table** (S1-13, PR #270): on desktop with a precise pointer the checkbox is a 16 px target, and WCAG 2.5.8 (axe `target-size`, serious) needs 4 px clear around it. With `pr-0` on the checkbox cell (the shadcn recipe) and the `-mx-2` of `TableSortButton`, a table of many columns – each at its narrowest – put the header checkbox right against the first sort button; only the E2E on the desktop caught it. The checkbox cell keeps `px-2` on desktop; `SelectableSortableTable` of `table.stories.tsx` (`w-auto`, so no width is shared out) is the story test of that case. A table story with few columns spreads spare width over the columns and hides such spacing problems.
- **Inline Combobox in a Popover or Drawer with several triggers** (#279 Phase 3, 2026-11-10): the ticket filter bar renders the picker as `<Combobox inline open multiple>` inside one `Popover` (tablet+) or `Drawer` (phones) whose triggers are **Add filter** and every chip (`PopoverTrigger`/`DrawerTrigger` with an `id`, controlled `open` and `triggerId`; the popup anchors to the active trigger). Base UI's default `initialFocus` focuses the first tabbable element unless *it* saw a touch – a step change or an open it did not detect as touch then focused the search input: `initialFocus` returns the popup element for a touch, and the bar records the pointer type itself (`onPointerDownCapture`/`onKeyDownCapture` on the bar – events of the portalled popup bubble there too) and passes `autoFocus` to the picker, which focuses its input in an effect (the lazily loaded picker mounts after the popup opened). A chip whose last value is unticked stays rendered while its picker is open (anchor and `finalFocus`). The page used to key the whole list by its address, which remounted the bar and closed the picker on every toggle – only the results are keyed now (`ticket-list.tsx`). jsdom tests of the web app have no jest-dom matchers (`toHaveFocus`, `toHaveAttribute`): compare `document.activeElement` and `getAttribute()`; `userEvent.pointer({ keys: '[TouchA]', target })` gives a `pointerType` of `touch`. In `multiple` mode a press on an item clears the input with the reason `input-clear`: a picker that keeps its search between choices takes the search only from `input-change`. The body between `DrawerHeader` and `DrawerFooter` needs `overflow-y-auto` (PR #290 review): the sheet is at most `100dvh - 6rem` high, so on a phone in landscape (740 × 360) a list without its own scroll slides under **Done**, whose footer then takes every press on those rows – the E2E "reaches every field of the bottom sheet on a phone in landscape" guards it. The popover has the same trap (UI QA of PR #290, D2): `PopoverContent` is a flex column capped at `max-h-(--available-height)` (Base UI sets the variable on the positioner, the popup inherits it), but a flex child keeps `min-height: auto`, so the field list spilled 12 px past the popup at 780 × 360 – the scrolling child needs `min-h-0 overflow-y-auto` (with `-m-1 p-1` for the focus ring). A chip's **×** and **Clear filters** remove the pressed button itself, so the focus fell to `<body>` (WCAG 2.4.3, D1): the bar moves it first – to the next chip's name, else the previous one, else **Add filter** – before it calls `onFiltersChange`.
