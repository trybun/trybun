# GitHub – agent identity, tokens and the ruleset

Non-obvious behaviour of GitHub and Cezar for the agents' GitHub identity. Decision: [ADR 0011](../../docs/adr/0011-maintainer-account-and-workflow-approval.md) (supersedes [ADR 0005](../../docs/adr/0005-github-app-as-agent-identity.md) and [ADR 0001](../../docs/adr/0001-github-identity-of-ai-agents.md)); rules: [§2.14](../../docs/spec/02-agent-rules.md), [§16.5](../../docs/spec/16-open-source.md). Entries marked *(app, until 2026-10-28)* describe the GitHub App `dtk7c2-claude` of ADR 0005 and matter only while it is still installed.

- **Since 2026-10-28 (ADR 0011)** the project's agents act with the maintainer's account: `gh auth login` and `gh auth setup-git` on the agents' machine, no `GH_TOKEN`. They may review, approve and merge only in the workflows the maintainer runs (`SDLC.md`); GitHub rejects approving one's own PR, so `om-approve-merge-pr` skips its approval step for the agents' PRs and merges after its gates. They never merge a change of requirements (change specification, specification change for approval, ADR) and never change repository settings, rulesets, environments, secrets or `v*` tags, although the account technically can.
- Migration done 2026-10-29 (ADR 0011): the `gh` wrapper `~/.local/bin/gh` stays earlier on `PATH` only until the maintainer's other projects (`RckikSystem3` next, `cezar-sandbox`, `om-skills-knowledge`) leave the app too – then the wrapper, the token helper, the private key and the app itself are deleted – and it no longer serves `trybun` (owners in `~/.config/dtk7c2-claude/config.json`), so in this repository `gh` is the maintainer's login; the repository's git config has no app credential helper, the global `gh auth git-credential` applies. A `gh auth login` must call `/usr/bin/gh` while the wrapper serves the current owner.
- The ruleset "Protect main" requires a pull request, the required status checks and squash, and no approval; only accounts with write access can merge, so contributors never merge their own pull requests. `CODEOWNERS` only requests the maintainer's review.

- *(app, until 2026-10-28)* The project's own agents (run by the maintainer through Cezar) act as the GitHub App `dtk7c2-claude` (`dtk7c2-claude[bot]`, Client ID `Iv23lisffmzAobQs3APE`, installed on `trybun` for `trybun/trybun` only); the maintainer `@dtk7c2` is the only code owner. External contributors' agents use their contributor's own account and fork instead. Before pushing, `gh api /installation/repositories --jq .total_count` must print a number: it answers only to an installation token, never to a user's token – never push or open a PR as anyone else.
- *(app, until 2026-10-28)* On the VPS (outside the repository): `~/.local/bin/dtk7c2-claude-token <owner>` mints and caches the installation token (1 hour, renewed 5 minutes before expiry) from the private key `~/.config/dtk7c2-claude/private-key.pem`; `~/.config/dtk7c2-claude/config.json` lists the owners it serves. `~/.local/bin/gh` wraps `/usr/bin/gh` and sets `GH_TOKEN` from the helper in repositories of those owners, unless `GH_TOKEN` is already set. Never put the token in a fixed `GH_TOKEN` (Cezar forwards it to every agent and it expires after an hour), and never add the Administration permission to the app.
- *(app, until 2026-10-28)* `gh auth login` on a shared OS user switches `gh` for every project of that user; the `gh` wrapper keeps the app limited to the allowlisted owners. Cezar forwards `HOME`, `GH_CONFIG_DIR` and `GH_TOKEN` to all agents, so the cockpit and every agent use the same identity.
- *(app, until 2026-10-28)* An SSH remote pushes as the owner of the SSH key, whatever `gh` says. Keep `origin` on https (`https://github.com/trybun/trybun.git`). The repository's own git config sets `credential.https://github.com.helper` to an empty value (resetting the global `gh auth git-credential`) followed by `~/.local/bin/dtk7c2-claude-git-credential trybun`; worktrees share it.
- The squash commit takes the PR title: the PR title must be a valid Conventional Commit; its scope, if any, comes from the closed list ([§2.14](../../docs/spec/02-agent-rules.md)).
- Every commit of a PR is checked too (`Commit messages and title`, `scripts/check-commit-messages.js`), against the same closed scope list: the om-* skills write `docs(runs): …` for their execution plans in `.ai/runs/`, but `runs` is not a scope – use `docs(agents): …` (2026-10-29, #113 needed a force-push to reword two commits). Check before pushing: `npx commitlint --from origin/main --to HEAD`.
- *(app, until 2026-10-28; replaced by ADR 0011)* ~~Never approve a PR with the agent identity, and never merge one the maintainer has not approved.~~ The rule followed from the required approval by a code owner, which the ruleset no longer has.
- *(app, until 2026-10-28)* Cezar's cockpit merge button runs as the app and works only when GitHub allows the merge; Cezar has no approve action. Its review gate, `gate.human` and QA labels are conveniences, not security boundaries.
- *(app, until 2026-10-28)* Cezar 0.16 reads merge requirements only from `GET …/branches/{branch}/protection/required_status_checks` (classic branch protection, needs the Administration permission). With the ruleset and the app it gets 403, so its merge button stays disabled until "Merge without waiting for requirements" is checked; GitHub still enforces the ruleset. Rulesets are readable with `GET …/rules/branches/{branch}`.
- GitHub added `require_extra_approval_for_unattributed_changes: true` to the "Protect main" ruleset by default. It is undocumented – if a PR stays blocked after the maintainer's approval, check this option first and record the finding here.
- *(app, until 2026-10-28)* The app (Contents and Workflows write) can push a branch whose workflow receives repository secrets, or push a tag that triggers a release. Release credentials are therefore stored only in the environments `release-please` and `release`, and `v*` tags are protected by a tag ruleset whose only bypass actor is the release app `trybun-release` ([ADR 0006](../../docs/adr/0006-release-pipeline.md), set up by the maintainer); never push `v*` tags.
- *(app, until 2026-10-28)* Required status checks are part of the "Protect main" ruleset, which the app (no Administration permission) cannot change: the maintainer adds them. A check name is the job `name:` of a workflow (e.g. `Format and lint`), and it must have run once on a pull request before the ruleset UI offers it; renaming a job silently drops it from the required checks.
- Workflows of pull requests run on `pull_request` (never `pull_request_target`) with `contents: read`, and pass `github.event.pull_request.title` through an environment variable, never inline in `run:` (script injection).
- On 2026-10-21 GitHub silently flagged `dtk7c2-2` (no banner for the account): its profile, PRs and issues returned 404 to everyone else, tab counters still counted them while the lists hid them, and its PRs started no workflows (0 check suites). Check any account without logging in: `curl -s -o /dev/null -w '%{http_code}' https://api.github.com/users/<login>` (404 = hidden). Likely trigger: a new account creating ~15 issues within minutes – create issues in small batches (the app's 15 issues in a row stayed visible). A reinstatement request (support.github.com → "I can login, but my profile and contributions aren't visible to others") got only automated replies for days, and a flagged account cannot delete itself. Since 2026-10-23 the agents act as the GitHub App instead ([ADR 0005](../../docs/adr/0005-github-app-as-agent-identity.md)); the account's issues #8–#22 and PR #23 were recreated as #25–#39 and #40. `dtk7c2-2` is no longer used: removed from the organization, logged out of `gh` on the VPS, and its deletion requested from GitHub Support – once deleted, its issues, PRs and comments show `@ghost` as author, while its squash commits keep `dtk7c2-2 <dtk7c2.2@gmail.com>`.
- **DCO and Dependabot** (S0-16): the job `DCO sign-off` (`.github/workflows/commitlint.yml`, `scripts/check-dco.js`) checks every commit of a pull request for a `Signed-off-by` with the author's name and e-mail; it exempts merge commits and Dependabot (`49699333+dependabot[bot]@users.noreply.github.com`), which cannot sign off. The commit-range step of `Commit messages and title` (`scripts/check-commit-messages.js`) exempts Dependabot too (#52): Dependabot guesses the subject case from the repository history and writes `fix(deps): Bump …`, which fails `subject-case`, and its `commit-message` options cannot force lower case. The exempt list lives in `scripts/pull-request-commits.js`. The PR title is still checked – lower-case `Bump` in the title of a Dependabot PR before merge. The maintainer adds `DCO sign-off` to the required checks of "Protect main" after its first run. Squash commits on `main` are authored by the app without sign-off – never run the script over `main`'s history. The app cannot read the organization's 2FA requirement (`two_factor_requirement_enabled` is `null` without the Administration permission) nor the fork workflow approval setting (403): the maintainer checks both.
- *(app, until 2026-10-28)* **Code scanning alerts and the daily image scan** (S0-19, 2026-10-25): the app needs the repository permission **Code scanning alerts: Read** to list alerts (`gh api 'repos/trybun/trybun/code-scanning/alerts?tool_name=Trivy&state=open'`); without it the API returns 403 "Resource not accessible by integration". A permission added to the app takes effect only after the owner of the installation accepts it: organization settings → GitHub Apps → `dtk7c2-claude` → Configure → "Review request" → "Accept new permissions"; until then the token still gets 403. The Cezar automation "Issues for alerts of the daily image scan" (a schedule, daily at 06:30 UTC, after the scan of `.github/workflows/image-scan.yml` at 04:43 UTC) relies on it: it opens one issue per vulnerability with the label `image-scan` and the hidden marker `<!-- image-scan:<ID> -->`, and comments on the open issue when more images are affected. Its definition lives in Cezar's state, not in the repository – a change of the alert categories `image-scan/<service>/<slot>` or of the tool name `Trivy` must be matched in its prompt.
- *(app, until 2026-10-28)* **Re-running CI and cleaning up branches** (2026-10-25): the app cannot re-run a workflow (`gh run rerun` → "Resource not accessible by integration", no Actions write permission); after a flaky job (e.g. a Lighthouse LCP or TBT outlier) push an empty signed-off commit `chore: run CI again after …` – the squash merge drops it. Nothing deletes local branches after a merge: GitHub deletes only the remote head branch, `git fetch --prune` (`fetch.prune true` is set in the repository) removes only `origin/*` refs and leaves the local branch `[gone]`, `git branch --merged` cannot see squash-merged branches, and Cezar keeps the `cez/<id>` branch and the worktree under `.ai/cezar/worktrees/` of every finished task – a worktree also blocks deleting its branch. Clean up after merges: `git worktree remove` for clean worktrees of finished tasks, then `git branch -D` for branches whose PR is merged (`gh pr list --state all --search <sha>`) or that are ancestors of `origin/main`.
- **Merging a child task's branch** (Cezar, S1-01): `scripts/check-commit-messages.js` lints every commit of the pull request, merge commits included, and commitlint ignores only Git's default merge subjects (`Merge branch '…' into …`). Merge with `git merge --no-ff <branch> -m "Merge branch '<branch>' into <target>"` – a custom subject fails the check; the DCO check skips merge commits.
