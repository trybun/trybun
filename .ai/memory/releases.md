# Releases – release-please, images and GitHub

Non-obvious behaviour found when the release pipeline was built (S0-11, October 2026). Decision: [ADR 0006](../../docs/adr/0006-release-pipeline.md); rules: [§2.11](../../docs/spec/02-agent-rules.md), [§15.4](../../docs/spec/15-deployment.md).

- **release-please reads its configuration from GitHub**, from the target branch, not from the checkout: a configuration file written by a workflow step is never used, and a change of `release-please-config*.json` takes effect only once merged into that branch. Hence the two committed files (`release-please-config.json` and `release-please-config.maintenance.json`, kept equal except `versioning` by `scripts/release.spec.js`).
- **Manifest `0.0.0` means "never released"**: without `initial-version`, release-please proposes `1.0.0` for the first release, whatever the commits and `bump-minor-pre-major`. `initial-version: 0.1.0` gives the Stage 0 version of the plan.
- **`prerelease: true`** marks every GitHub Release with a `0.x` version as a pre-release, not only `-rc` versions, and the `prerelease` versioning strategy needs it to produce `-rc` versions at all – the reason release candidates are tagged by the release workflow instead (ADR 0006).
- **The action's version inputs** (`release-as`, `versioning-strategy`) apply only without a manifest; in manifest mode everything comes from the configuration file.
- **`draft: true` needs `force-tag-creation: true`**: GitHub creates the tag of a draft only when it is published, and release-please then cannot find the previous release and puts the whole history into the next changelog.
- **Release pull requests and `GITHUB_TOKEN`**: events caused by `GITHUB_TOKEN` start no workflows (except `workflow_dispatch` and `repository_dispatch`), so a release pull request opened with it never gets the required checks. The release app's token avoids it. Its commits have no `Signed-off-by`; `scripts/pull-request-commits.js` exempts `<id>+trybun-release[bot]@users.noreply.github.com`.
- **GHCR** accepts `GITHUB_TOKEN` or a classic personal access token, not a GitHub App token. A package pushed by a workflow is linked to the repository through the label `org.opencontainers.image.source` and starts private.
- **Trivy of the `postgres` image** (2026-10-24, Trivy 0.76.0): the base image `pgvector/pgvector:0.8.7-pg18-trixie` has two `CRITICAL` findings – CVE-2026-6653 of Debian's `libxml2` (no fixed version) and CVE-2025-68121 of the Go standard library in `/usr/local/bin/gosu` (fixed in newer Go). `web` and `server` had none. Reproduce locally: `docker buildx build --load -t trybun-scan/postgres docker/postgres` and `docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy:0.76.0 image --scanners vuln --severity CRITICAL --exit-code 1 trybun-scan/postgres`.
- **The `aquasecurity` organization** has an IP allow list: `gh api repos/aquasecurity/…` with the agents' app token returns 403; unauthenticated `curl https://api.github.com/repos/aquasecurity/…` and `git ls-remote` work.
- **`docker compose` with `image:` and `build:`** may build instead of pull when the image is missing; the deployment package therefore drops the `build:` sections (`scripts/build-deployment-package.js`), so a missing image fails instead of building from absent sources.
