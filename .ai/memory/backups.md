# Backups, restores and updates

Non-obvious behaviour found when the backup service and the commands `backup`, `restore` and `update` of `./trybun` were built (S0-13, October 2026). Rules: [§13.6](../../docs/spec/13-non-functional.md), [§15.7](../../docs/spec/15-deployment.md), [§15.10](../../docs/spec/15-deployment.md).

- **restic** (0.19): `cat config` exits with 10 when the repository does not exist and 12 for a wrong password – `docker/backup/backup.sh` creates a repository only on 10. Every snapshot uses `--host trybun`, otherwise a new server (another container host name) finds no "latest" snapshot. `restore <snapshot>:/backup/set --target …` restores the content of the folder without its path.
- **Keycloak**: an access token of the realm's `admin-cli` client (password grant) has no `sub` claim in the `trybun` realm; the ID token (`scope=openid`) has it – the restore test compares the `sub` of the ID token.
- **pg_restore**: `DROP DATABASE … WITH (FORCE)` from the database `postgres`, then `pg_restore --dbname=postgres --create`, recreates a database with its owner (`keycloak` for the Keycloak database), so the role must exist – the init script of `docker/postgres` creates it. `pg_dump` 18.x of another minor version than the server works.
- **Database passwords**: the volume keeps the passwords it was initialised with, so a `.env` restored over a newer installation does not match; `./trybun restore` sets both roles' passwords with `ALTER ROLE` through `docker compose exec -T postgres psql` over the local socket (trusted in the image) and stdin, never on a command line.
- **Docker Compose**: `depends_on` with `required: false` lets `backup` depend on `seaweedfs` when its profile is off. `docker compose config --images` lists only the images of enabled services. `docker compose pull` fails for images that exist only locally (a locally built test release); `./trybun update` pulls only images missing on the server (`docker image inspect` first), before it changes anything. `COMPOSE_PROJECT_NAME` overrides the top-level `name:` and shell variables override `.env`, which lets the restore test run next to another installation without ClamAV.
- **Test network**: containers of any Compose bridge network reach a port the host publishes on the gateway of Docker's default bridge (`172.17.0.1`); the restore test runs its "external" S3 storage there.
- **postgres Alpine image** ships `/usr/local/bin/gosu` with the critical Go standard library vulnerability CVE-2025-68121 (see `releases.md`); the backup image removes it, since it never runs the server's entry point. The official image's tag is rebuilt only with a PostgreSQL or Alpine release, so an Alpine package fix (e.g. `brotli-libs` 1.2.1-r0 for CVE-2026-111497, 2026-10-30) can be missing even from the newest digest – check with `docker run --rm <base> sh -c 'apk update -q && apk list -u'`; the Dockerfile then upgrades just that package with `apk upgrade --no-cache <package>` until a rebuilt base ships it. rclone prints a notice on every run without a configuration file – `RCLONE_CONFIG=/dev/null` silences it; the remote `objects` comes from `RCLONE_CONFIG_OBJECTS_*` variables, which `configure_storage` of `backup.sh` exports from `TRYBUN_S3_*` (since S1-08 phase 4; `compose.yaml` no longer sets them). `rclone cat` of a missing object in an existing bucket prints nothing and exits 0; only a missing bucket gives exit code 3 – `marker()` treats both as "no marker".
- **POSIX sh**: `set -e` does not apply inside a function called as a condition (`if ! store …`), so such functions return explicitly. In BusyBox sh (the backup image is Alpine) it does not apply inside a command substitution either: in `state=$(owner)`, a failing `marked=$(marker)` inside `owner` would not stop it, so the function ends such steps with `|| exit 1` and the caller writes `state=$(owner) || exit 1`. The same holds for a whole subshell on the left side of `||` or `&&` (#249, 2026-11-07): `(backup daily) || log …` let a failing `pg_dump` go on and store an incomplete set, so `schedule` runs the subshell as its own command with `set -e` inside, between `set +e` and `set -e`, and checks `$?`. Replacing the running `./trybun` by `mv` (a rename) is safe – the shell keeps reading the old file.
- **`flock` on an `exec`-opened descriptor lasts as long as the shell** (0.1.2–0.2.0, found on the test VPS 2026-10-26): `lock()` opens fd 9 with `exec` and locks it, so the long-running `schedule` held the lock from its first daily backup on, and every later one-off `backup`, `fetch` and `restore-data` (`./trybun backup`, `update`, `restore`, `uninstall` with S3) waited forever on `flock 9`. The daily backup runs in a subshell now; the restore test runs a scheduled backup before `./trybun backup`. Workaround on an affected installation: `docker compose restart backup`.
- **`./trybun restore --storage-url <url>`** (2026-11-07): `storage-owner <url>` runs before the configuration is restored, so it gets the URL as an argument and reads the credentials from the fetched `.env`; `restore-data` needs no argument, because it runs after the restored `.env` was rewritten and Compose interpolates the new `TRYBUN_S3_URL` into the container (a `TRYBUN_S3_URL` exported in the shell would override it – the restore test unsets it before its restores). `restore-data` therefore checks again that the folder in use lies outside the backup's one. The restore test keeps its copy folder in the existing bucket `trybun-attachments`, since a new bucket on the test's SeaweedFS costs volumes (see `docker.md`).
- **A test restore must not keep production's off-site repository** (2026-11-07, S1-08 Q25, revised the same day): every server backs up as `--host trybun`, so a test server with production's `TRYBUN_BACKUP_S3_URL` would write into that repository and its `forget --keep-daily` would prune production's snapshots. `./trybun restore --test` therefore empties `TRYBUN_BACKUP_S3_URL` (the URL alone decides, see `repositories()` of `backup.sh`); `--storage-url` is accepted only with `--test`, and `--test` of a backup on an external storage needs `--storage-url`. After a `./trybun backup` of the test copy, its local volume has the newest snapshot, so a later `restore latest` on that server fetches the copy, not the backup – the restore test drops server d's volumes before its next restore.
- **Reading `.env` like Compose** (checked with Compose 5.6, 2026-11-07): Compose accepts `export ` (also with a tab), leading blanks, blanks around `=` and `KEY: value`; an unquoted value ends at ` #` (a space – a tab before `#` stays part of the value, and `KEY= #x` gives `#x`), trailing blanks are dropped, `\r` is ignored, a quoted value ends at its quote, the last assignment wins. `sed -n 's/^KEY=//p'` misses or misreads all of these; `backup.sh` and `deploy/trybun` share the awk function `ENV_VALUE`. Check a case with a throw-away `compose.yaml` and `docker compose config`.
- **rclone and buckets** (1.75, 2026-11-07): without `no_check_bucket`, every write (`rcat`, `sync` into the storage) first sends `CreateBucket` (`PUT /bucket`), which an access key limited to a folder may not; `configure_storage` sets `RCLONE_CONFIG_OBJECTS_NO_CHECK_BUCKET=true` for provider `Other`, and `restore-data` creates a missing bucket with the connection-string override `rclone mkdir "objects,no_check_bucket=false:<bucket>"` (it beats the `RCLONE_CONFIG_OBJECTS_*` setting; check with `--dump headers`). SeaweedFS creates a missing bucket on `PutObject` by itself, so neither the restore test nor a SeaweedFS container shows a missing-bucket failure – the stub of `docker/backup/backup.spec.js` does.
- **Testing `backup.sh` without containers**: `docker/backup/backup.spec.js` runs it with `TRYBUN_BACKUP_DATA`, `TRYBUN_BACKUP_INSTALL` and `TMPDIR` pointing into a temporary folder and stubs of rclone (buckets as folders), restic and the PostgreSQL tools; a `sleep` stub that sends TERM to its parent ends `schedule` after its start. The image runs BusyBox sh and awk: check new shell or awk constructs once with `docker run --entrypoint sh ghcr.io/trybun/backup:<version>`.
- **Free disk for the restore test** (2026-11-07): its external SeaweedFS runs with the default 1 GB volumes and sizes its volume count from the free disk, so with ~10 GB free the second bucket (`trybun-attachments`) got `InternalError` on its first write (`rclone rcat` in "Backing up the attachment folder of the external storage"); with 16 GB free it passed. Since 2026-11-07 the test starts it with `-master.volumeSizeLimitMB=64`, like the integration tests (`docker.md`). Check `df -h /` first; `docker builder prune -f` frees the unused build cache.
