# Backups, restores and updates

Non-obvious behaviour found when the backup service and the commands `backup`, `restore` and `update` of `./trybun` were built (S0-13, October 2026). Rules: [§13.6](../../docs/spec/13-non-functional.md), [§15.7](../../docs/spec/15-deployment.md), [§15.10](../../docs/spec/15-deployment.md).

- **restic** (0.19): `cat config` exits with 10 when the repository does not exist and 12 for a wrong password – `docker/backup/backup.sh` creates a repository only on 10. Every snapshot uses `--host trybun`, otherwise a new server (another container host name) finds no "latest" snapshot. `restore <snapshot>:/backup/set --target …` restores the content of the folder without its path.
- **Keycloak**: an access token of the realm's `admin-cli` client (password grant) has no `sub` claim in the `trybun` realm; the ID token (`scope=openid`) has it – the restore test compares the `sub` of the ID token.
- **pg_restore**: `DROP DATABASE … WITH (FORCE)` from the database `postgres`, then `pg_restore --dbname=postgres --create`, recreates a database with its owner (`keycloak` for the Keycloak database), so the role must exist – the init script of `docker/postgres` creates it. `pg_dump` 18.x of another minor version than the server works.
- **Database passwords**: the volume keeps the passwords it was initialised with, so a `.env` restored over a newer installation does not match; `./trybun restore` sets both roles' passwords with `ALTER ROLE` through `docker compose exec -T postgres psql` over the local socket (trusted in the image) and stdin, never on a command line.
- **Docker Compose**: `depends_on` with `required: false` lets `backup` depend on `seaweedfs` when its profile is off. `docker compose config --images` lists only the images of enabled services. `docker compose pull` fails for images that exist only locally (a locally built test release); `./trybun update` pulls only images missing on the server (`docker image inspect` first), before it changes anything. `COMPOSE_PROJECT_NAME` overrides the top-level `name:` and shell variables override `.env`, which lets the restore test run next to another installation without ClamAV.
- **Test network**: containers of any Compose bridge network reach a port the host publishes on the gateway of Docker's default bridge (`172.17.0.1`); the restore test runs its "external" S3 storage there.
- **postgres Alpine image** ships `/usr/local/bin/gosu` with the critical Go standard library vulnerability CVE-2025-68121 (see `releases.md`); the backup image removes it, since it never runs the server's entry point. The official image's tag is rebuilt only with a PostgreSQL or Alpine release, so an Alpine package fix (e.g. `brotli-libs` 1.2.1-r0 for CVE-2026-111497, 2026-10-30) can be missing even from the newest digest – check with `docker run --rm <base> sh -c 'apk update -q && apk list -u'`; the Dockerfile then upgrades just that package with `apk upgrade --no-cache <package>` until a rebuilt base ships it. rclone prints a notice on every run without a configuration file – `RCLONE_CONFIG=/dev/null` silences it; the remote `objects` comes from `RCLONE_CONFIG_OBJECTS_*` variables, which `configure_storage` of `backup.sh` exports from `TRYBUN_S3_*` (since S1-08 phase 4; `compose.yaml` no longer sets them). `rclone cat` of a missing object in an existing bucket prints nothing and exits 0; only a missing bucket gives exit code 3 – `marker()` treats both as "no marker".
- **POSIX sh**: `set -e` does not apply inside a function called as a condition (`if ! store …`), so such functions return explicitly. In BusyBox sh (the backup image is Alpine) it does not apply inside a command substitution either: in `state=$(owner)`, a failing `marked=$(marker)` inside `owner` would not stop it, so the function ends such steps with `|| exit 1` and the caller writes `state=$(owner) || exit 1`. Replacing the running `./trybun` by `mv` (a rename) is safe – the shell keeps reading the old file.
- **`flock` on an `exec`-opened descriptor lasts as long as the shell** (0.1.2–0.2.0, found on the test VPS 2026-10-26): `lock()` opens fd 9 with `exec` and locks it, so the long-running `schedule` held the lock from its first daily backup on, and every later one-off `backup`, `fetch` and `restore-data` (`./trybun backup`, `update`, `restore`, `uninstall` with S3) waited forever on `flock 9`. The daily backup runs in a subshell now; the restore test runs a scheduled backup before `./trybun backup`. Workaround on an affected installation: `docker compose restart backup`.
- **`./trybun restore --storage-url <url>`** (2026-11-07): `storage-owner <url>` runs before the configuration is restored, so it gets the URL as an argument and reads the credentials from the fetched `.env`; `restore-data` needs no argument, because it runs after the restored `.env` was rewritten and Compose interpolates the new `TRYBUN_S3_URL` into the container (a `TRYBUN_S3_URL` exported in the shell would override it – the restore test unsets it before its restores). The restore test keeps its copy folder in the existing bucket `trybun-attachments`, since a new bucket on the test's SeaweedFS costs volumes (see `docker.md`).
