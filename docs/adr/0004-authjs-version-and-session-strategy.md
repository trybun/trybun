# 0004 – Auth.js version and session strategy

- Status: proposed
- Date: 2026-10-21, completed in S0-05 on 2026-10-23
- Deciders: the maintainer (`@dtk7c2`)
- Specification: [§14.2](../spec/14-architecture.md), [§14.4](../spec/14-architecture.md), [§13.5](../spec/13-non-functional.md)

## Context and problem statement

The web application signs users in with Auth.js and the Keycloak provider and keeps **server-side sessions** (Auth.js `database` strategy with the Prisma adapter); the cookie holds only an opaque session ID, and tokens never reach the browser ([§14.2](../spec/14-architecture.md), [§14.4](../spec/14-architecture.md)). The specification requires Auth.js from its **stable release line**; if the App Router integration existed only as a pre-release, the chosen version would need an ADR approved by a human (Rule 10).

The state of the Auth.js package `next-auth` on npm on 2026-10-21:

- `latest`: **4.24.15** (2026-07-20) – the stable line. It supports the App Router (Route Handler for `/api/auth/*`, `getServerSession()` in Server Components and Route Handlers) and Next.js 12.2–16 (peer dependency `next: ^12.2.5 || ^13 || ^14 || ^15 || ^16`).
- `beta`: **5.0.0-beta.32** (2026-07-20) – version 5, in beta since October 2023, with the App Router-first API (`auth()`).

Which version does Trybun use, and how are the sessions stored?

## Decision drivers

- Rule 10: stable versions only; a pre-release needs a human decision.
- The BFF of [§14.4](../spec/14-architecture.md): server-side sessions, the encrypted refresh token on the server, serialized token refresh, back-channel logout.
- Prisma ORM 7 as the only database client ([§14.2](../spec/14-architecture.md)).

## Decision outcome

**`next-auth` 4.24 (stable line)**, because its App Router integration is stable, so no pre-release is needed. Session strategy as specified:

- `session.strategy: 'database'` with a session adapter on Prisma (see "Confirmed in S0-05"); the session cookie (`httpOnly`, `Secure`, `SameSite=Lax`) holds only the opaque session token;
- the Keycloak access and refresh tokens are kept on the server only; the refresh token is stored encrypted; the refresh with rotation is implemented in the session handling of `lib/auth` and serialized per session;
- the session lifetimes follow the table of [§14.4](../spec/14-architecture.md) per account kind.

### Confirmed in S0-05

S0-05 implemented the sign-in with `next-auth` 4.24.15 on Next.js 16.4 and confirmed or settled the open points:

- **Adapter: an own session adapter on Prisma** (`apps/web/src/lib/auth/session-adapter.ts`) instead of `@next-auth/prisma-adapter` or `@auth/prisma-adapter`. Both packaged adapters need the Auth.js models `User`, `Account`, `Session` and `VerificationToken` and create a `User` from the OAuth profile on the first sign-in. That conflicts with the account model of [§7.4](../spec/07-users-organizations-permissions.md): accounts are created only by invitations and the first-run wizard, the `User` model has required fields of its own (`kind`) and no `name`, `image` or `emailVerified`, and the web application must not decide about accounts. The own adapter implements only the methods the OAuth flow with database sessions calls (`getUserByAccount`, `createSession`, `getSessionAndUser`, `updateSession`, `deleteSession`); the "user" of Auth.js is the Keycloak user (`sub`), and the API resolves the account from the access token. Auth.js 4 checks adapter methods only for the e-mail provider, which is not used.
- **Session table**: `sessions` in the Prisma schema of `apps/server`, so there is one schema and one migration history ([§14.6](../spec/14-architecture.md)). The schema has a second generator (`web`) whose client is generated by `apps/web` itself (`prisma generate --generator web` on install); the web application uses only this table. The row holds a SHA-256 hash of the session token (never the token), the Keycloak user (`sub`) and session (`sid`), and the access and refresh tokens.
- **Token encryption**: JWE (`dir`, `A256GCM`) with `jose`, key derived from `AUTH_SECRET` with HKDF-SHA-256; the tokens never leave the server (`/api/auth/session` returns only `expires`).
- **Getting the tokens into the session row**: Auth.js 4 passes the OAuth tokens to the `signIn` callback but not to `createSession`. The Route Handler builds the options per request with a request-local slot: the `signIn` callback stores the tokens there, and `createSession` of the same request reads them. No state is shared between requests.
- **Token refresh with rotation and its serialization per session** belong to the BFF proxy (S0-08), the first code that uses the access token; the row already holds what it needs (encrypted refresh token, access-token expiry).
- **Back-channel logout**: `POST /api/auth/backchannel-logout` (a specific Route Handler next to the catch-all of Auth.js), called by Keycloak over the internal network and not routed by Caddy. It verifies the logout token with `jose` against the JWKS and deletes the sessions of its `sid`. Sign-out deletes the row and ends the Keycloak session through the logout endpoint with the refresh token.
- **Environment variables**: Auth.js 4 reads `NEXTAUTH_URL` (there is no `AUTH_URL` in version 4) and accepts `AUTH_SECRET`; [§15.3](../spec/15-deployment.md) names them accordingly.
- **Prisma ORM 7** works in the web application with its driver adapter `@prisma/adapter-pg`.
- **Module interoperability**: TypeScript with `nodenext` types the default import of the CommonJS modules of `next-auth` as the whole module, while Turbopack resolves it to `exports.default`; `lib/auth/next-auth.ts` resolves both cases in one place.

### Consequences

- Good: a stable release line, as Rule 10 requires; no human exception needed.
- Good: version 4 is widely deployed with the App Router and receives releases (4.24.15 in July 2026).
- Bad: version 4 has the older API (`getServerSession(authOptions)` instead of `auth()`); a later move to version 5 changes `lib/auth`, which is the only place the session is read ([§18.5](../spec/18-code-patterns.md)).
- Good: the own adapter is about one hundred lines without Auth.js models; the database keeps one account model.
- Bad: the own adapter must follow the adapter contract of Auth.js; a move to version 5 rechecks it (its integration tests cover the contract the flow uses).

## Considered options

1. **`next-auth` 4.24 (stable)** – chosen.
2. **`next-auth` 5 beta** – the newer API, but a pre-release for three years; it would need a human exception to Rule 10 and could change before its stable release.
3. **JWT session strategy** – rejected by the specification ([§14.5](../spec/14-architecture.md)): a JWT cookie cannot be revoked and exceeds the cookie size limit with Keycloak tokens.
