# 0002 – Technology stack

- Status: proposed
- Date: 2026-10-21
- Deciders: the maintainer (`@dtk7c2`)
- Specification: [§14.2](../spec/14-architecture.md), [§14.5](../spec/14-architecture.md), [§14.6](../spec/14-architecture.md), [§17.1](../spec/17-conventions.md), [§18.3](../spec/18-code-patterns.md), [§18.9](../spec/18-code-patterns.md)

## Context and problem statement

The specification chooses the technologies of Trybun and the alternatives it rejected ([§14.2](../spec/14-architecture.md), [§14.5](../spec/14-architecture.md)). Task S0-01 of the [implementation plan](../plan/implementation-plan.md) records them as an ADR, pins the versions the monorepo starts with, and verifies the one choice that depended on a new framework feature: validation and serialization with the native Standard Schema support of NestJS 12, with the fallback NestJS 11 with `nestjs-zod` if the verification failed.

Which versions does the project start with, does the NestJS 12 approach work end to end, and which tools enforce the conventions and boundaries of [§17.1](../spec/17-conventions.md) and [§18.9](../spec/18-code-patterns.md)?

## Decision drivers

- Rule 1: the conventions of each technology, no in-house framework ([§18.1](../spec/18-code-patterns.md)).
- Rule 10: latest stable versions after a 7-day cooldown, no pre-releases.
- One validation library (Zod) for requests, responses, forms and the OpenAPI document ([§14.4](../spec/14-architecture.md)).
- Boundaries between packages and layers checked in CI, not by review alone ([§14.6](../spec/14-architecture.md), [§18.9](../spec/18-code-patterns.md)).

## Decision outcome

The stack of [§14.2](../spec/14-architecture.md) is adopted unchanged. The monorepo starts with these versions (latest stable releases published by 2026-10-14, the 7-day cooldown of Rule 10):

| Component | Version | Note |
|---|---|---|
| Node.js | 24.22.0 (LTS "Krypton") | `.node-version`; 24.22.1 (2026-10-20) is within the cooldown |
| pnpm | 12.13.0 | `packageManager`; `minimumReleaseAge: 10080` enforces the cooldown on every install |
| Turborepo | 2.11.8 | |
| TypeScript | 6.0 | **not 7.0**, see below |
| NestJS | 12.1.3 (`@nestjs/swagger` 12.0.2, CLI 12.0.8) | 12.2.0 (2026-10-19) is within the cooldown |
| Next.js / React | 16.4.1 / 19.3.1 | React Compiler 1.0 (`babel-plugin-react-compiler`) |
| Zod | 4.6.7 | |
| ESLint | 10.12.0 with `typescript-eslint` 8.71 | |
| Vitest | 5.0.4 | |

**TypeScript 6.0 instead of 7.0.** TypeScript 7.0 (the native compiler, July 2026) is the latest stable release, but `typescript-eslint` 8.71 supports `typescript <6.1.0`, the NestJS 12 CLI depends on `typescript ~6.0.2` and `@nestjs/swagger` 12 on `^5.5.0 || ^6.0.0`. The project moves to TypeScript 7 when these tools support it (monthly dependency review, [§2.10](../spec/02-agent-rules.md)).

**Validation with the NestJS 12 Standard Schema support – verified.** A verification endpoint in the test of the request pipeline (`apps/server/src/platform/http/http.module.spec.ts`) confirms on NestJS 12.1.3, `@nestjs/swagger` 12.0.2 and Zod 4.6.7:

- the global `StandardSchemaValidationPipe` with `errorHttpStatusCode: 422` and one `exceptionFactory` returns `422` with `errors[]` (JSON Pointer and code per field) for an invalid body;
- the global `StandardSchemaSerializerInterceptor` with the schema declared by the project's response decorator (`@ResponseSchema()`, combining `@SerializeOptions({ schema })` and `@ApiResponse({ standardSchema })`) strips a field outside the response schema, and returns `500` for a response that does not match it;
- the OpenAPI document generated by `@nestjs/swagger` from the same schemas describes the request body (including `minLength`/`maxLength`) and the response;
- `openapi-typescript` 7.13 generates types from that document that compile with `openapi-fetch` 0.17 in strict mode; a field outside the response schema is a type error.

The fallback NestJS 11 with `nestjs-zod` is therefore not needed. `openapi-typescript` 7.13 declares a peer dependency on TypeScript 5 only; it works with TypeScript 6 in the verification above and is allowed through `peerDependencyRules.allowedVersions` in `pnpm-workspace.yaml`.

**Lint tooling for conventions and boundaries.** `@trybun/eslint-config` enforces [§17.1](../spec/17-conventions.md) and [§18.9](../spec/18-code-patterns.md) with widely used rules, without a dedicated architecture plugin:

| Check | Rule |
|---|---|
| Identifiers | `@typescript-eslint/naming-convention` |
| File and folder names (kebab-case; App Router segments in `src/app`) | `eslint-plugin-check-file` |
| Package boundaries ([§14.6](../spec/14-architecture.md)) | `@typescript-eslint/no-restricted-imports` with the allowed `@trybun/*` packages of each package; `import-x/no-relative-packages` |
| Layers: `platform` ↛ `modules`; web `app` → `features` → `lib` | `import-x/no-restricted-paths` |
| No NestJS, Prisma or clock reading in `domain/`; no Prisma in controllers, gateways and processors; no Radix UI or vaul | `no-restricted-imports`, `no-restricted-syntax` |
| A `schema` on every `@Body`, `@Query`, `@Param`, `@MessageBody` | `no-restricted-syntax` |
| No cycles between modules or features | `import-x/no-cycle` |
| No `process.env` outside the configuration, no `console`, no default exports outside framework files | `no-restricted-properties`, `no-console`, `import-x/no-default-export` |
| No string literals in JSX, no `asChild` | `no-restricted-syntax` |
| Rules of React and the React Compiler | the `recommended` preset of `eslint-plugin-react-hooks` 7, every rule as an error |

Each check has test cases in `packages/eslint-config/src/configs.spec.js`, reported and accepted; the naming cases run with type information, the cycle case on fixture files.

### Consequences

- Good: one schema per request and response serves validation, serialization, the OpenAPI document and the typed web client; no DTO classes and no third-party validation layer.
- Good: the cooldown of Rule 10 is enforced by pnpm itself, not only by review.
- Good: the boundary rules are plain ESLint rules with test cases; a new layer rule is one more pattern or zone.
- Bad: the project stays on TypeScript 6 until its tools support TypeScript 7.
- Bad: path-based rules (`no-restricted-imports` patterns, `no-restricted-paths` zones) depend on the folder layout of [§18.3](../spec/18-code-patterns.md) and [§18.5](../spec/18-code-patterns.md); a change of the layout changes the rules in the same pull request.

## Considered options

1. **NestJS 12 with its Standard Schema support** (chosen, verified).
2. **NestJS 11 with `nestjs-zod`** – the fallback of [§14.5](../spec/14-architecture.md); not needed.
3. **`eslint-plugin-boundaries`** for the layer rules – the common dedicated plugin; not chosen because version 7 changed its configuration model and the needed checks are covered by core and `import-x` rules that the project already uses.
4. **TypeScript 7.0** – rejected for now, unsupported by `typescript-eslint` and the NestJS CLI.
