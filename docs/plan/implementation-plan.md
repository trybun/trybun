# Trybun – implementation plan

This plan splits the implementation of the specification ([`docs/spec/`](../spec/README.md)) into stages. Each stage ends with a **working, deployable system** that is better than the previous one. The **MVP (Minimum Viable Product)** is delivered in the first stages (0 and 1); later stages extend the working system.

## How to use this plan

- Every task below is meant to be **one pull request** ([§2.14](../spec/02-agent-rules.md)). If a task turns out larger, split it before starting and update this plan in the same PR.
- Every task lists the specification sections it implements. Read them (and the glossary) before starting.
- Tasks that deliver functionality (Stages 1–8) start with a **change specification** in `.ai/specs/` approved through its own pull request ([§2.8](../spec/02-agent-rules.md)). Infrastructure tasks of Stage 0 may skip it, except S0-10 and S0-12, which deliver user-facing behaviour and start with a change specification.
- Every task follows the **Definition of Done** ([§2.13](../spec/02-agent-rules.md)): conventions, minimum user steps, user docs, tours, README, reusable components, project memory, up-to-date specification, phone and tablet support, dependency security, versioning, code patterns, tests, CI gates, human review.
- Every task writes code with the **code patterns** of [§18](../spec/18-code-patterns.md) (Rule 12). The tasks listed in [§18.9](../spec/18-code-patterns.md) build the **reference implementation** of a pattern; tasks of the same group that use the pattern follow §18 and align with the reference when they rebase on `main`.
- The **"Done when"** column lists checkable statements that must hold in addition to the Definition of Done. They rely only on the task itself and on tasks of earlier groups or stages. A change specification may refine them, never weaken them.
- **"Out of scope"** notes name parts of the referenced sections that belong to a later task. Do not build them early, and do not add placeholder models or UI for them.
- **Cross-cutting parts grow with the features.** S0-12 provides the getting-started checklist with the items available in Stage 0, S1-04 the permission layer with the rules for projects, organizations and accounts, and S1-16 anonymization and data export for the data of Stage 1. Each task after them extends these parts for what it introduces: its permission rules in the same CASL abilities and its `allowedActions` ([§18.3](../spec/18-code-patterns.md)), with an allowed and a denied test for each of its rows of [§7.5](../spec/07-users-organizations-permissions.md); its personal data in anonymization and export ([§13.2](../spec/13-non-functional.md)); its item of the getting-started checklist ([§15.6](../spec/15-deployment.md)), if it has one.
- Tasks within a stage are listed in a sensible order; tasks marked with the same group number can be done in parallel.
- A stage is finished when all its tasks are merged and its **exit criteria** are met. Each finished stage is released ([§15.4](../spec/15-deployment.md)) and deployed to the test environment.
- Task status is tracked in this file: `[ ]` open, `[x]` done.

## Stage 0 – Foundation

**Goal:** a deployable skeleton that already follows every rule: monorepo, CI quality gates, Docker Compose, login through Keycloak, translations, component library, documentation and tour infrastructure. No business features yet.

**Exit criteria:**

- `git clone` + `pnpm install && pnpm dev` starts the full local environment ([§15.12](../spec/15-deployment.md)).
- A release package installs on a clean Linux VPS with the install script; the first-run wizard creates the Administrator; HTTPS works.
- A user can log in (Keycloak), switch language EN/PL and see an empty, translated application shell.
- All CI gates run on every pull request.
- ADRs record at least: the stack decisions of [§14](../spec/14-architecture.md), the Auth.js version and session strategy, the server bundling and module system, the attachment serving design and the invitation flow.

## Stage 1 – MVP

**Goal:** the system is usable in production. End users report tickets in a project; the team handles them through the list and the Kanban board, communicates with public comments and internal notes, and everyone is notified. Organizations and visibility protect customer data from the start.

**Exit criteria:**

- An Administrator creates a project and an organization, a Project manager invites team members and end users.
- An end user creates a ticket (with attachments and visibility) from the portal ([§5.7](../spec/05-visibility-and-search.md)), sees its public status and replies in comments.
- The team handles the ticket through statuses on the list and the Kanban board, with internal notes and assignment; resolution confirmation works with explicit "Yes, solved" / "No, still a problem" actions.
- Sharing requests are approved or refused from the "Pending sharing approvals" view.
- Watchers receive in-app and e-mail notifications for the events of [§6.6](../spec/06-comments-notifications.md) that exist in Stage 1.
- GDPR baseline works: data export, deletion request, anonymization, redaction of content and its history.
- User documentation exists for all MVP views, and the tours "First login", "Creating a ticket" and "Kanban board" exist.
