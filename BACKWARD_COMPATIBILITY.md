# Backward compatibility

This file defines the **protected contract surfaces** of Trybun: what self-hosting Administrators, integrations and existing installations depend on, and how a change to each must be handled. Review skills check pull requests against it; implementation skills warn when a change violates it.

It is derived from the surfaces the repository actually has. The rules themselves live in the specification – this file only maps them to paths and links them. When this file and the specification disagree, the specification wins and this file is fixed (Rule 8).

## 1. Versioning and approval

- **One product version** for the whole monorepo (`MAJOR.MINOR.PATCH`), derived by **release-please** from Conventional Commits ([§2.11](docs/spec/02-agent-rules.md#211-rule-11--versioning), [`release-please-config.json`](release-please-config.json), [ADR 0006](docs/adr/0006-release-pipeline.md)). Maintenance branches `release/X.Y.x` bump PATCH only ([`release-please-config.maintenance.json`](release-please-config.maintenance.json)).
- A breaking change is **always** marked with `!` after the type/scope (`feat(deploy)!: …`) or a `BREAKING CHANGE:` footer. The footer says **what the Administrator has to do**; it ends up in the release notes and is shown by `./trybun update` before the update ([§15.7](docs/spec/15-deployment.md#157-updates)).
- **MAJOR** = anything that needs the Administrator's attention: a renamed or removed environment variable or configuration option, a manual update step, a removed feature, removal of an old public API version, higher server requirements ([§2.11](docs/spec/02-agent-rules.md#211-rule-11--versioning)).
- **Before `1.0.0`** (`bump-minor-pre-major: true`): breaking changes bump MINOR, but they **must still be marked** – the marker drives the release notes and the update confirmation. No breaking change has been released yet ([`CHANGELOG.md`](CHANGELOG.md)).
- Agents never set versions, never edit `CHANGELOG.md` and never write a `Release-As:` footer.
- **Who approves**: a breaking change or a change of requirements needs a **change specification approved by a human** (merged in its own PR, [§2.8](docs/spec/02-agent-rules.md#28-rule-8--the-specification-is-kept-up-to-date), [`.ai/specs/README.md`](.ai/specs/README.md)) and the human review of the implementation PR. A changed technical decision needs an ADR ([`docs/adr/`](docs/adr/README.md)). A human releases by merging the release PR.
- **Upgrade path**: any version of a MAJOR series updates directly to its latest release; a new MAJOR goes through the latest release of the previous series, which is when old migrations and compatibility code may be removed ([§2.11](docs/spec/02-agent-rules.md#211-rule-11--versioning)).

## 2. Protected surfaces

"Required path" abbreviations: **BC** = mark as breaking (`!` / `BREAKING CHANGE:` with the Administrator's steps), **CS** = change specification approved by a human, **Spec** = update `docs/spec/` in the same PR, **ADR** = new or superseding ADR, **Docs** = update `README.md` / `deploy/INSTALL.md` / `docs/user/` (EN + PL) in the same PR.

## 3. Not protected (do not over-block)

These may change in a normal `feat`/`fix`/`refactor` PR without a breaking marker, as long as all consumers in the repository are updated in the same PR and CI is green:

- **Workspace packages** `@trybun/ui`, `@trybun/contracts`, `@trybun/i18n`, `@trybun/tsconfig`, `@trybun/eslint-config` – all `"private": true`, consumed as source via `workspace:*`, never published ([§14.6](docs/spec/14-architecture.md#146-monorepo-structure)). Their TypeScript exports are internal. (Exception: the **error codes** and future **token scopes** in `@trybun/contracts` – see above.) If `@trybun/sdk` is ever published, it becomes protected.
- **BFF internals** of `apps/web`: the proxy implementation of `/api/v1/[...path]`, Auth.js routes (`/api/auth/*`), `/api/health`, server components, features, `proxy.ts` – as long as the public URLs above keep working.
- **Internal API process details**: NestJS modules, `/health` and `/health/ready` (internal network only, used by `compose.yaml` of the same release), the server image command line `node dist/cli.js <command>` (called only by `deploy/trybun` of the same release).
- **Outbox events and queue job names/payloads** (`outbox_events`, BullMQ) – internal. Jobs and outbox events written by an earlier release survive `./trybun update` (delayed timers, failed jobs kept for retry), so job data changes additively: a new field is optional with a defined behaviour when missing, no field is removed or renamed, and a removed job or event type keeps its processor. The rule and its window are proposed in the change specification of [#108](https://github.com/trybun/trybun/pull/108); TODO: replace this line with a link to §17.2 once it is approved.
- **Help page URLs** (`/help/<audience>/<category>/<name>`) – internal until a redirect mechanism for help pages exists: a renamed or removed page updates every link to it in the repository (other docs, product tours, the getting-started checklist, texts) in the same PR. When the mechanism arrives, help URLs move to the public URLs above.
- **Translation keys and texts** in `packages/i18n/` (except `errors.<code>`, which follows the codes), UI layout, product tours, Storybook stories.
- **Repository tooling**: `scripts/`, CI workflows other than the release/image contract, lint configuration, `compose.dev.yaml`, the demo dataset (`apps/server/prisma/demo-dataset.ts`, `seed.ts`).
- **Specification and docs wording** – versioned with the code; only the requirements they describe are protected (Rule 8).

## 4. Checklist for a PR touching a protected surface

- [ ] Identified which row(s) of section 2 the change touches; no protected surface changed "by accident" in a refactor.
- [ ] Preferred an **additive** change (new variable with a default, new endpoint/field, new error code, new migration, new event `version`) over a modification or removal.
- [ ] If breaking: a **change specification** in `.ai/specs/` was approved by a human (merged) before the implementation.
- [ ] Commit/PR title marked with `!` or a `BREAKING CHANGE:` footer that states the Administrator's exact steps (pre-1.0 too).
- [ ] Deprecation instead of removal where the spec requires it (API versions, webhook versions: `Deprecation`/`Sunset`, ≥ 1 MAJOR).
- [ ] Database: new forward-only migration, no edits to merged migrations, no silent data loss; `./trybun update` from the previous release runs unattended.
- [ ] `./trybun restore` of a backup from the previous release still works (restore test in CI).
- [ ] `.env.example`, `deploy/INSTALL.md`, `README.md`, `AGENTS.md` commands and `docs/user/` (EN + PL) updated as affected (Rules 3, 5).
- [ ] `docs/spec/` updated in the same PR (`docs(spec): …` commit); ADR added if a technical decision changes.
- [ ] `pnpm api:generate` run if endpoints changed; `pnpm lint` (Prisma, help, Keycloak theme checks) green.
- [ ] No version numbers or `CHANGELOG.md` edited by hand.
